# 业务编号规则设计说明

## 一、设计目标

系统需要为团单、应收单、应付单、交易流水等核心业务对象自动生成编号。编号设计需要满足以下目标：

1. **系统唯一**  
   同一组织内编号不能重复，系统需要通过唯一索引和并发控制保证编号唯一。

2. **业务可读**  
   编号需要能体现业务类型、所属组织和生成时间，方便计调、财务人员查询、沟通和对账。

3. **规则稳定**  
   编号一旦生成，不随团单日期、客户、供应商、金额等业务信息变化而自动变更。

4. **配置简单**  
   第一版仅允许组织设置一次“组织业务前缀”，其他编号规则由系统统一控制。

---

## 二、组织业务前缀规则

组织业务前缀在【组织管理】中设置，用于生成团单编号、应收单号、应付单号和交易流水号。

| 项目 | 规则 |
|---|---|
| 字段名称 | 组织业务前缀 |
| 设置位置 | 组织管理 / 组织信息 |
| 长度限制 | 2 到 4 位 |
| 字符范围 | 仅支持大写英文字母 A 到 Z |
| 是否允许数字 | 不允许 |
| 是否允许中文 | 不允许 |
| 是否允许特殊符号 | 不允许 |
| 是否必填 | 必填 |
| 是否可修改 | 设置后不可修改 |
| 是否唯一 | 建议全系统唯一 |
| 生效范围 | 用于该组织后续生成的业务编号 |

### 示例

```text
XTB
XAT
SLD
TYL
KLT
```

### 不允许的示例

```text
XA01
T1
小团
XT-B
xtb
```

### 设计说明

组织业务前缀不建议允许数字。数字会和后面的日期、流水号连在一起，降低编号可读性。

例如：

```text
XA012026070001
```

该编号容易让用户分不清 `XA01` 是组织前缀，还是 `01` 属于日期或流水号。改为纯字母后，结构更清晰：

```text
XAT2026070001
```

## 四、编号整体规则

系统编号采用统一结构：

```text
业务类型前缀 + 组织业务前缀 + 日期 + 流水号
```

其中：

| 组成部分 | 说明 | 示例 |
|---|---|---|
| 业务类型前缀 | 标识业务对象类型 | AR、AP、TX |
| 组织业务前缀 | 标识所属组织 | XTB、SLD |
| 日期 | 标识生成年月或年月日 | 202607、20260708 |
| 流水号 | 系统自动递增 | 0001、000001 |

团单编号作为核心业务编号，直接使用组织业务前缀开头。财务类编号使用业务类型前缀开头，便于区分不同单据类型。

## 五、团单编号规则

团单编号是计调和业务人员最常用的编号，需要保持简洁。

### 生成规则

```text
组织业务前缀 + 年月 + 4位流水号
```

### 示例

```text
XTB2026070001
SLD2026070001
TYL2026070001
```

### 字段说明

| 部分 | 含义 |
|---|---|
| XTB | 组织业务前缀 |
| 202607 | 生成年月 |
| 0001 | 当月流水号 |

### 递增规则

团单编号按组织、年月独立递增。每个组织每月从 `0001` 开始生成。

## 六、应收单编号规则

应收单属于财务单据，建议使用 `AR` 作为固定前缀。

### 生成规则

```text
AR + 组织业务前缀 + 年月 + 6位流水号
```

### 示例

```text
ARXTB202607000001
ARSLD202607000001
ARTYL202607000001
```

### 字段说明

| 部分 | 含义 |
|---|---|
| AR | 应收单 |
| XTB | 组织业务前缀 |
| 202607 | 生成年月 |
| 000001 | 当月流水号 |

### 递增规则

应收单按组织、年月独立递增。应收单编号生成后不可修改。

## 八、交易流水号规则

交易流水用于记录实际资金收支，建议使用 `TX` 作为固定前缀。

### 生成规则

```text
TX + 组织业务前缀 + 年月日 + 6位流水号
```

### 示例

```text
TXXTB20260708000001
TXSLD20260708000001
TXTYL20260708000001
```

### 字段说明

| 部分 | 含义 |
|---|---|
| TX | 交易流水 |
| XTB | 组织业务前缀 |
| 20260708 | 交易日期 |
| 000001 | 当日流水号 |

### 递增规则

交易流水按组织、日期独立递增。收入、支出不在编号中区分，通过交易方向字段记录。

```text
交易方向：收入 / 支出
```

这样可以兼容收款、付款、退款、手续费、调整款等多种资金场景。

## 十一、系统实现建议

1. **业务编号不作为数据库主键**  
   数据库主键建议使用 UUID、雪花 ID 或自增 ID。业务编号作为唯一业务字段。

2. **组织业务前缀只能设置一次**  
   前缀为空时允许保存；保存成功后字段锁定，不允许再次修改。

3. **编号生成后不可修改**  
   财务相关编号必须保持稳定，避免影响核销、对账和历史追溯。

4. **流水号按组织独立递增**  
   不同组织之间拥有各自的流水号序列。

5. **需要防止并发重复**  
   后端生成编号时需要使用事务、序列表或数据库锁，并对编号字段增加唯一索引。

6. **建议保存编号生成记录**  
   可以建立编号序列表，按组织、业务类型、年月或日期维护当前流水值。

7. **组织业务前缀建议全系统唯一**  
   这样即使未来跨组织导出、集团化管理、多组织查询，也能避免编号识别混乱。

## 十二、第一版推荐落地方案

第一版建议开放最少配置项，减少用户理解成本。

| 配置项 | 是否开放给组织 | 说明 |
|---|---|---|
| 组织业务前缀 | 开放 | 2 到 4 位，大写英文字母，仅可设置一次 |
| 日期规则 | 不开放 | 系统统一控制 |
| 流水位数 | 不开放 | 团单 4 位，财务单据 6 位 |
| 单据类型前缀 | 不开放 | AR、AP、TX 系统固定 |
| 是否允许手动改编号 | 不建议开放 | 第一版建议所有业务编号均由系统自动生成 |

最终推荐：

```text
团单编号：XTB2026070001
应收单号：ARXTB202607000001
应付单号：APXTB202607000001
交易流水号：TXXTB20260708000001
```


核销单号推荐规则

建议使用：

CL + 组织业务前缀 + 年月 + 6位流水号

其中 CL 表示核销单，可以理解为 Clearing / Clear。

示例：

CLXTB202607000001
CLSLD202607000001
CLTYL202607000001
二、为什么用 CL

核销单的作用是把一笔或多笔资金流水，匹配到一笔或多笔应收、应付单据上，本质属于财务处理记录。

用 CL 的好处是：

编号	含义
AR	应收单
AP	应付单
TX	交易流水
CL	核销单

这样财务中心里的编号体系比较完整，也方便以后扩展退款单、结算单、调整单等。

三、核销单号生成规则
项目	规则
编号前缀	CL
组织前缀	使用组织业务前缀
日期规则	年月
流水位数	6 位
递增规则	按组织、年月独立递增
是否允许修改	不允许
是否允许手动录入	不允许
是否作为主键	不作为数据库主键
