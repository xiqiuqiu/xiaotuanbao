# 小团宝 AI Agent 化改造产品交接文档

## 一、文档目的

本文用于向产品、设计、研发团队同步小团宝 AI 改造的整体构想、当前系统基础、核心业务理解、用户目标以及后续需要调整的产品方向。

本轮讨论的核心命题是：

**如何让小团宝从一个依赖用户理解页面、字段和流程的专业 SaaS，逐步演进为一个围绕用户业务目标进行理解、规划、审核和执行的 AI Agent 系统。**

当前阶段不追求立即实现“完全无人值守的自动发团”。

更现实的路径是，在保留小团宝现有专业业务模型、权限体系、表单和领域规则的基础上，逐步建立一层面向用户目标的 AI 交互和业务编排能力。

---

# 二、业务背景与问题理解

## 2.1 当前小团宝的业务特点

小团宝面向中小地接旅行社的计调、财务和管理人员，核心工作围绕一次发团生命周期展开。

一个典型业务流程包含：

**创建发团 → 客源 → 游客 → 行程 → 资源 → 应收 → 应付 → 收付款 → 核销 → 结清**

这些对象之间存在比较强的前后依赖。

例如：

- 通常需要先有发团，才能继续维护该团下面的内容。
- 需要先建立客源单，后续才能形成对应应收。
- 行程、资源和供应商信息又会影响应付。
- 财务操作建立在前面业务事实已经形成的基础上。

因此，目前的小团宝在产品形态上天然是一套“按业务阶段、业务对象和页面组织”的 SaaS。

这种设计本身符合复杂业务系统的要求，但也带来一个典型问题：

**系统的数据模型和用户的思考模型并不完全一致。**

---

# 三、用户真实目标

用户进入小团宝时，通常不会先思考：

> 我要填写哪些字段？

他们真正思考的是：

> 我要把这个团建起来。

或者：

> 这是客户给我的名单、行程、报价和聊天记录，帮我把这次发团需要的东西整理好。

再比如：

> 这个团还缺什么？

> 哪些客人还没录完整？

> 哪些费用还没有生成？

因此，用户天然携带的是一个**业务目标**，而系统当前暴露给用户的是大量：

- 页面
- 模块
- 字段
- 表单
- 状态
- 前后依赖

对于熟练用户，这些结构能提高效率。

对于新用户，这些结构本身就构成了学习成本。

因此，本轮 AI 改造需要坚持一个核心产品原则：

> **AI 面向用户目标，业务系统面向数据模型。**

用户可以继续表达业务语言，AI 负责把这些内容映射到小团宝内部的业务对象、字段和操作流程。

---

# 四、目标产品形态

长期来看，希望用户可以通过一个类似 ChatGPT、Codex 的入口，自然输入和上传与一次发团有关的资料。

例如：

> 9 月 5 日新疆 8 日团，16 个人。  
> 这是客户名单、微信截图、行程 PDF 和酒店报价。  
> 帮我把团建起来。

系统随后完成：

1. 理解用户目标。
2. 检查上传资料。
3. 从不同资料中识别业务事实。
4. 判断当前哪些信息已经齐全。
5. 判断哪些信息仍存在缺失或冲突。
6. 形成业务执行计划。
7. 让用户确认。
8. 按计划逐步创建或修改业务对象。
9. 在必要位置请求人工审核。
10. 自动引导进入下一个业务阶段。
11. 持续告诉用户“现在完成了什么，还缺什么，下一步是什么”。

最终体验应逐渐从：

> 用户学习系统，再按照系统结构完成工作。

演进为：

> 用户说明目标和事实，由系统负责组织完成路径。

---

# 五、Agent 产品结构构想

当前建议把用户感知层面的 Agent 分成三个场景。

## 5.1 全局 Agent

入口位于全局工作台。

它主要解决：

> “我想完成什么？”

用户可以从这里直接开始一个业务任务，而无需首先寻找某个功能菜单。

例如：

> 帮我建一个 9 月 5 日出发的新疆团。

> 看一下我刚上传的这些资料，能不能开始建团。

> 帮我检查这个团目前还缺什么。

全局 Agent 更接近一个业务 Planner 和 Orchestrator。

它需要理解：

- 用户目标
- 当前 Organization
- 用户权限
- 上传资料
- 已存在的业务对象
- 当前流程状态

然后形成一个可执行 Plan。

---

## 5.2 页面级 Agent

进入某个具体业务页面后，可以通过右侧抽屉继续和 Agent 对话。

页面 Agent天然拥有当前页面上下文。

例如用户进入客源页面后，Agent 应当知道：

- 当前是哪个发团。
- 当前有哪些客源单。
- 已经录入多少游客。
- 哪些信息缺失。
- 当前是否存在待审核内容。

用户可以直接说：

> 把刚才那份名单录到这里。

或者：

> 还有哪些人信息不完整？

这种 Agent 的价值是减少用户理解字段和页面结构的负担。

---

## 5.3 流程级 Agent

流程级 Agent 的目标是持续回答：

> “下一步应该做什么？”

例如：

发团创建完成后，系统可以主动建议：

> 已经完成基本团单信息。下一步建议整理客源和游客。

客源完成以后：

> 16 位游客已经全部识别完成，可以开始生成行程。

行程完成以后：

> 行程已经完整，但第 4 天酒店报价仍缺失，因此暂时无法完整生成应付。

这一层最终会让小团宝从“菜单驱动的软件”逐渐增加“任务推进驱动”的体验。

---

# 六、技术实现层面建议采用“一套 Agent Runtime，多种 Context Scope”

虽然产品体验可以分成全局 Agent、页面 Agent和流程 Agent，但底层不建议真正建设三套完全独立的 Agent。

更合理的结构是：

**一套统一 Agent Runtime，根据入口使用不同的 Context Scope。**

例如：

### 全局 Context

包含：

- Organization
- User
- 用户目标
- 当前上传资料
- 相关业务对象
- 当前 Plan

### 发团页面 Context

增加：

- departureId
- 当前发团状态
- 当前业务阶段
- 当前审核状态

### 客源页面 Context

进一步增加：

- 当前客源单
- 游客列表
- 人数差异
- 应收状态

这样可以避免未来出现三套：

- 对话机制
- 权限机制
- 审核机制
- Workflow
- Agent 工具

底层能力应当统一。

---

# 七、Plan Mode 设计构想

全局 Agent 不建议收到请求后立刻产生大量业务写入。

建议引入类似当前代码 Agent 常见的 Plan 模式。

用户提出目标之后，Agent 先生成业务计划。

例如：

### 本次准备完成

发团

- 创建「9 月 5 日北疆 8 日团」
- 出团日期：9 月 5 日
- 回团日期：9 月 12 日
- 预计 16 人

客源

- 创建 A 旅行社客源单，10 人
- 创建 B 旅行社客源单，6 人

游客

- 导入 16 位游客

行程

- 创建 8 日行程
- 第 4 日住宿信息缺失

财务

- 当前资料可以形成部分应收
- 酒店报价未完整，因此暂不完整生成应付

用户首先确认：

> “系统准备完成哪些业务动作？”

确认之后，再进入执行。

Plan 本身属于一个相对高层的“业务意图确认”。

它和后续具体业务数据审核属于两个不同层次。

---

# 八、审核机制的当前基础

目前小团宝已经具备较完整的 AI 审核包机制。

现有设计中：

1. Agent 从用户对话、OCR、文件解析等资料中识别候选字段。
2. Agent 生成一份待审核候选。
3. 候选被持久化为服务端审核包。
4. 用户需要明确“应用”或“放弃”。
5. 未确认候选不会直接进入正式业务草稿。
6. 后续新输入不会自动覆盖前一份仍未处置的审核包。
7. 用户可以查看字段填写依据。
8. 候选来源可以追溯到用户对话、OCR 结果或其他资料证据。

现有 ADR 也明确规定，高密度审核应继续发生在业务表单中，聊天区主要展示状态和审核入口，避免形成聊天和表单两套确认机制。

这一机制非常重要，应当保留。

---

# 九、审核机制预期调整

当前审核主要偏向：

> “AI 建议填写哪些字段？”

下一阶段建议逐渐提升为：

> “AI 准备完成哪些业务对象和业务动作？”

也就是把审核层级从字段进一步向业务层提升。

建议形成三层结构：

## 第一层：业务目标

例如：

> 完成新疆 8 日团建团。

## 第二层：业务对象 / Action

例如：

- 创建发团
- 创建两个客源单
- 导入 16 位游客
- 生成行程
- 创建资源
- 生成应收

## 第三层：字段和 Evidence

用户展开某个业务对象后，再看到：

- 客户名称
- 人数
- 单价
- 日期
- 联系人
- 证据来源

这种结构可以显著降低用户审核压力。

用户首先确认：

> “这件事情对不对？”

需要时再确认：

> “某个字段为什么这样填？”

长期目标是：

**业务审核优先，字段审核下沉。**

---

# 十、为什么不能简单取消表单

Agent 化不意味着传统表单会消失。

复杂 SaaS 依然需要：

- 精细查看
- 专业修改
- 批量操作
- 业务校验
- 财务核对
- 异常处理

因此更合理的变化是：

**表单逐渐从“主要输入入口”变成“业务事实检查与精细编辑界面”。**

用户可以通过 AI 完成大部分资料整理和录入。

需要确认细节时，再进入表单。

---

# 十一、现阶段已经具备的 AI 基础

本轮已经基于实际仓库代码进行核对。

当前小团宝已经具备一批比较关键的 Agent 基础设施。

包括：

- AI Create Task
- AiConversation
- AiInputBatch
- Workflow Worker
- Context Manifest
- AI Review Package
- OCR / Material Parse
- Agent Tool
- 持久化会话和状态恢复

仓库已经将完整会话、后台可靠执行和当前模型上下文拆为不同层次。

因此后续 Agent 化不需要从零重新建立会话系统和执行基础设施。

---

# 十二、当前资料和 OCR 上下文机制

这是本轮讨论中特别重要的一点。

用户未来可能一次提供：

- 多个 PDF
- 微信截图
- 手机截图
- 图片
- 行程单
- 报价单
- 游客名单
- 其他文件

如果每一次都把全部 OCR 结果直接放进大模型上下文，会很快受到上下文窗口、成本和推理噪声的限制。

目前代码已经部分解决了这个问题。

---

## 12.1 当前已经存在固定解析版本

每个输入批次会固定：

`materialId + parseResultVersion`

因此某一次 Agent 执行看到的资料版本是稳定的。

即使后续同一资料重新 OCR，也不会悄悄改变正在运行的批次上下文。

---

## 12.2 当前已经支持按资料、按页读取

代码已经实现：

`getMaterialParseResultForAgent()`

Agent 在需要深入查看某份资料时，可以通过：

- materialId
- parseResultVersion
- pageNumber

读取指定解析结果。

服务端还会校验该资料和解析版本确实属于当前 inputBatch。

因此当前已经具备：

> Agent 按需深入读取资料

的基础能力。

---

## 12.3 当前 Context Builder 会先提供资料摘要式投影

目前系统仍然会将每份资料的一小段 excerpt 放入当前模型上下文。

Context Builder 有明确总字符预算。

超出预算时会：

1. 优先丢弃较旧的 Agent 消息。
2. 再裁剪资料 excerpt。

因此当前结构更接近：

**完整 OCR → 资料索引 / excerpt → Agent 判断需要什么 → Tool 精确读取指定资料 / 页面。**



这个方向适合继续发展。

---

# 十三、当前 Context 机制仍存在的关键缺口

目前已经较好解决：

> 文件太大怎么办？

下一步需要解决：

> 一个业务流程很长怎么办？

当前 Context Builder 中：

`conversationBackground.summary = null`

滚动摘要暂未实现。

代码中明确仍然是：

> 本阶段无滚动摘要。



因此，当未来 Agent 从：

发团 → 客源 → 游客 → 行程 → 资源 → 财务

持续运行时，不能简单依靠越来越长的聊天历史作为上下文传递机制。

---

# 十四、预期增加 Workflow State / Plan State

建议未来将跨阶段上下文进一步抽象成结构化业务状态。

例如：

## Goal

完成 9 月 5 日新疆团建团。

## Confirmed Facts

- 出发日期：9 月 5 日
- 人数：16
- A 旅行社：10 人
- B 旅行社：6 人

## Completed Actions

- 发团已创建
- A 客源单已创建
- B 客源单已创建

## Unresolved Facts

- 第 4 日酒店缺失
- 酒店最终报价缺失

## Next Actions

- 导入游客
- 创建行程
- 补酒店资源

## Evidence References

记录相关：

- materialId
- parseResultVersion
- page
- conversation event
- business object

下一阶段只携带当前需要的：

- Workflow State
- 当前业务事实
- 当前业务对象
- 必要 Evidence 引用

而无需继续携带完整历史。

---

# 十五、未来 Context 的推荐分层

建议未来明确区分四类信息。

## 1. 原始资料层

PDF、截图、OCR、附件原文。

只持久化。

按需读取。

## 2. Evidence / Fact Layer

从资料中识别出的结构化事实。

例如：

- 客户
- 日期
- 人数
- 金额
- 游客
- 酒店
- 联系人

这些事实必须有来源。

## 3. Workflow State

当前业务已经完成什么、缺什么、下一步是什么。

## 4. Runtime Context

每次 Agent / Action 实际收到的最小上下文。

通过 Context Builder 动态组装。

这样可以降低对超长上下文窗口的依赖。

---

# 十六、AI Action Gateway 的规划基础

仓库中目前已经存在 AI Action Gateway 的 ADR 设计，但尚未全面落地实现。

设计的核心思想是：

Agent 不能直接调用业务服务完成任意修改。

Agent 首先提出一个 AI Action Proposal。

随后服务端完成：

1. 识别真实 Actor。
2. 识别真实 Target。
3. 检查 User 权限。
4. 检查 Agent Action Capability。
5. 判断业务风险。
6. 记录 Action Decision。
7. 决定：
   - Forward
   - Review
   - Reject
8. 只有 Forward 才真正产生业务效果。



这个设计与本轮产品方向总体兼容。

---

# 十七、Action Gateway 应坚持的产品边界

Gateway 更适合负责：

- Action 注册
- Actor
- Target
- 权限
- Agent Capability
- 风险等级
- Review Policy
- 幂等
- 审计

Gateway 不应复制业务领域规则。

例如：

> 一个已结清发团是否可以重新产生应付。

最终判断仍应由领域 Service 决定。

这样才能保证：

用户 UI、API、Agent

最终执行的是同一套业务规则。

---

# 十八、Action 应逐渐从字段操作升级成业务动作

未来 Action 不建议围绕：

- setDepartureDate
- setGuestCount
- setCustomerName

这类字段操作进行大量扩展。

更适合围绕业务语义建立：

- createDeparture
- createSourceOrder
- addTravelers
- createItinerary
- addResource
- submitReceivable
- submitPayable

字段只是 Action 的 payload。

这样 Planner 才能真正规划：

> “我要完成哪些业务动作？”

而不会退化成：

> “我要填哪些字段？”

---

# 十九、Plan 与 Action 的关系

未来建议采用：

**Goal → Plan → Action → Gateway → Business Service**

例如：

用户说：

> 帮我把这个团建好。

Planner 形成：

1. 创建 Departure。
2. 创建两个 Source Order。
3. 导入游客。
4. 创建 Itinerary。
5. 创建 Resource。
6. 提交 Receivable。

每一个 Action 再经过 Gateway。

Gateway 根据 Action 风险决定：

- 自动读取
- 自动执行
- 进入审核
- 拒绝

这样可以形成渐进式自动化。

---

# 二十、自动化等级建议

不建议第一阶段全部开放自动执行。

可以按照风险逐步开放。

## Level 1：Read

例如：

- 查询资料
- 查询路线
- 查询供应商
- 查询当前发团
- 检查缺失信息

可以高度自动化。

## Level 2：Suggest

例如：

- 建议团名
- 建议客源结构
- 建议行程
- 建议费用归属

由 AI 提议。

## Level 3：Review

例如：

- 创建发团
- 创建客源
- 批量导入游客
- 添加行程

AI 准备完成后由用户审核。

## Level 4：Execute

对于成熟、低风险、可恢复操作，可以逐渐允许用户授权自动执行。

## Level 5：High Risk

例如：

- 财务实质写入
- 不可逆动作
- 大额变更
- 影响已结算结果的操作

继续保持显式人工确认。

---

# 二十一、对现有产品结构的预期调整

第一阶段无需大规模重构现有页面。

可以继续保持：

- 发团
- 客源
- 游客
- 行程
- 资源
- 财务

这些专业业务页面。

AI 主要增加三种入口：

### 全局入口

面向目标。

### 页面右侧 Agent

面向当前业务对象。

### 流程提示

面向下一步。

随着 AI 能力成熟，再逐渐降低用户寻找页面和字段的频率。

---

# 二十二、核心体验原则

后续产品设计建议坚持以下原则。

### 1. 用户先看到业务结果

例如：

> 将创建两个客源单。

优先于：

> `partnerId = xxx`

### 2. AI 所有写入都可解释

用户应能查看：

> 为什么这样判断？

以及：

> 来源在哪里？

### 3. 未确认内容不能悄悄成为业务事实

特别是财务类和关键运营数据。

### 4. AI 不隐藏业务后果

例如：

> 此操作会重新打开已结清发团。

必须明确展示。

### 5. 用户不需要理解全部字段才能完成任务

这是 Agent 化最直接的用户价值。

### 6. Context 必须显式管理

不能依赖“大模型以后上下文会越来越长”。

需要通过：

- Material Index
- Evidence
- Facts
- Workflow State
- Context Builder

进行上下文编排。

# 二十三、对产品团队最重要的认知转变

过去设计小团宝时，主要问题是：

> 一个业务对象应该有哪些字段？

未来 Agent 化之后，需要增加一类新的设计问题：

> 用户为了完成这个业务目标，需要让系统知道哪些事实？

进一步再问：

> 哪些事实 AI 可以从资料中判断？

> 哪些事实必须询问用户？

> 哪些动作可以自动完成？

> 哪些动作需要审核？

> 哪些动作必须由人执行？

因此以后每一个业务模块除了：

**页面模型 + 数据模型**

还应逐渐拥有：

**Goal + Facts + Actions + Evidence + Review Policy**

这会成为 Agent 化业务设计的基本单位。

# 二十四、建议下一阶段重点产出

下一阶段建议优先整理一张：

# Agent Business Action Map

以完整发团生命周期为主线。

例如：

| 阶段 | 用户目标 | AI 可读取 | AI 可建议 | AI 可审核执行 | 高风险动作 |
|---|---|---|---|---|---|
| 发团 | 建立团单 | 路线、资料 | 团名、日期、人数 | 创建发团 | 特殊状态修改 |
| 客源 | 建立客源关系 | 客户资料 | 客源归属 | 创建客源单 | 已提交财务数据修改 |
| 游客 | 完成游客信息 | 名单、证件、截图 | 人员匹配 | 批量导入 | 敏感信息覆盖 |
| 行程 | 建立执行计划 | 行程单、路线 | 行程结构 | 创建行程 | 已执行行程调整 |
| 资源 | 安排行程资源 | 酒店、车辆、供应商 | 资源匹配 | 创建资源 | 已确认资源修改 |
| 应收 | 形成收入事实 | 客源、报价 | 应收金额 | 提交应收 | 财务变更 |
| 应付 | 形成成本事实 | 资源、报价 | 应付金额 | 提交应付 | 财务变更 |

完成这张图之后，可以进一步确定：

- Plan 应有哪些步骤。
- Gateway 应有哪些 Action。
- 哪些 Action 是 Review。
- 哪些 Action 可以自动执行。
- 每个 Action 需要哪些 Context。
- 哪些 Evidence 必须保存。
- 每个阶段 Agent 应如何提示下一步。

# 二十五、阶段性产品结论

当前小团宝已经拥有比较好的 AI 基础设施。

现阶段最大的机会，不在于继续增加一个更聪明的聊天框。

真正值得推进的是将已有的：

**对话理解 + OCR + 审核包 + Workflow + Context Builder**

进一步连接成：

**用户目标 → Plan → Business Action → Review → Execute → Next Step**

产品最终需要让用户感受到：

> “我只需要告诉小团宝我想完成什么，以及把我手里的资料给它。”

系统负责：

> “理解资料、整理事实、规划步骤、发现缺失、请求确认、完成操作，并告诉我下一步。”

这应当成为小团宝 AI Agent 化改造的长期方向。
