# 前端业务自动化测试框架设计

日期：2026-08-10
状态：已确认，待实施

## 1. 背景

当前项目已经具备 Web Vitest、API Jest E2E，以及 `apps/web-e2e` 下的 Playwright 本地冒烟测试。现有浏览器用例覆盖登录、工作台、发团主路径、财务页面可达性和一条新建发团薄写路径，但仍依赖人工挑选路径、长期本地数据和手动启动环境，无法回答以下问题：

- 前端业务代码中还有哪些角色、状态和操作分支从未被验证；
- 一次代码改动影响了哪些业务行为，应运行哪些测试；
- 自动化通过是否真正证明了持久化业务结果，而不只是页面出现成功提示；
- 哪些关键风险已经自动化，哪些仍是明确缺口。

本设计将现有 Playwright 样例升级为项目级“前端业务行为验证框架”。目标不是锁死所有 DOM 或追求代码行覆盖率，而是消除人工测试的路径盲区，持续证明关键业务入口、状态变化、角色权限和持久化结果正确。

## 2. 设计原则

### 2.1 全量登记，风险分级

所有可识别的前端业务行为都应进入候选发现和登记过程；持续执行按风险分级，只有关键和高风险行为必须获得相应强度的自动化证据。普通交互和展示行为不强制使用 Playwright。

参见 [ADR-0039](../../adr/0039-automation-coverage-by-risk.md)。

### 2.2 机器发现，人确认语义

路由、菜单、权限、代码区域和运行时界面用于自动发现候选行为；业务含义、风险、预期结果和验证层必须由人确认。AI 可以追踪代码并生成目录或测试草稿，但不能自行成为业务语义的权威来源。

参见 [ADR-0042](../../adr/0042-machine-discovered-human-confirmed-test-impact.md)。

### 2.3 原子行为与完整旅程分开

目录中的最小单位是：一个角色在明确前置状态下执行一次有业务意义的操作，并产生可观察的业务结果。孤立点击不是业务行为；完整生命周期由多个原子行为组合。

参见 [ADR-0039](../../adr/0039-automation-coverage-by-risk.md)。

### 2.4 每个行为只有一个主验证层

| 验证层 | 主要证明内容 |
| --- | --- |
| 单元测试 | 金额计算、条件判断、状态映射等纯逻辑 |
| 组件测试 | 表单分支、按钮状态、错误提示、前端状态更新 |
| API E2E | 权限、持久化状态、金额守恒、幂等、组织隔离 |
| Playwright | 用户入口可达、真实交互成功、可见结果正确 |
| 视觉回归 | 关键页面布局、遮挡、错位和外观变化 |

其他层只补充主层无法证明的内容，不跨层重复穷举同一断言。

参见 [ADR-0039](../../adr/0039-automation-coverage-by-risk.md)。

## 3. 总体架构

```text
代码结构 / 多角色运行时界面
              ↓
        候选行为发现器
              ↓
       人工确认业务语义
              ↓
  版本化 YAML 业务行为目录
              ↓
代码区域 → 业务能力 → 行为编号
              ↓
    影响分析与测试选择器
              ↓
场景工厂 → Playwright → API 辅助证据
              ↓
 PR 核心 smoke / 夜间全量 / 发版依据
              ↓
登记、自动化、通过、失配的风险报告
```

## 4. 业务行为目录

### 4.1 建议目录

```text
docs/testing/
  capabilities.yaml
  behaviors/
    auth.yaml
    departure.yaml
    source-order.yaml
    execution.yaml
    finance.yaml
    supplier.yaml
    partner.yaml
    product.yaml
    system.yaml
```

`capabilities.yaml` 维护代码区域与业务能力的映射；`behaviors/*.yaml` 是业务行为的唯一权威数据源。覆盖状态、测试路径和最近执行结果由工具计算，不在 YAML 中重复手工维护。

参见 [ADR-0039](../../adr/0039-automation-coverage-by-risk.md) 与 [ADR-0042](../../adr/0042-machine-discovered-human-confirmed-test-impact.md)。

### 4.2 行为结构

```yaml
- id: FIN-VERIFY-CANCEL
  title: 财务撤销核销
  capability: finance.verification
  actors:
    - finance
  preconditions:
    - 存在已核销收款及对应应收
  action: 撤销核销
  observableResults:
    - 未核销余额恢复
    - 核销历史仍可查看
  invariants:
    - 核销历史不得被删除
    - 流水与应收余额保持守恒
  risk: critical
  primaryLayer: playwright
  supportingLayers:
    - api-e2e
  lifecycle: active
```

规则：

- `id` 一经发布保持稳定，标题和文案变化不影响编号；
- `capability` 必须存在于能力目录；
- `risk` 只能是 `critical`、`high`、`normal`、`display`；
- `primaryLayer` 只能有一个；
- `lifecycle` 表示行为本身是否有效，不用于人工填写覆盖状态；
- 删除行为优先标记为 `deprecated` 并保留变更记录，再清理失效测试。

### 4.3 风险判断

风险由失败影响、发生可能和人工可发现性共同决定，而不是按页面重要性或使用频率主观决定。

| 风险 | 典型边界 |
| --- | --- |
| 关键 | 金额、权限、组织隔离、历史保留、不可逆操作、核心闭环 |
| 高风险 | 多状态、多角色、跨页面且失败后可恢复的操作 |
| 普通 | 容易发现和恢复的常规增删改查或局部交互 |
| 展示 | 不改变业务状态的呈现行为 |

参见 [ADR-0039](../../adr/0039-automation-coverage-by-risk.md)。

## 5. 测试关联协议

### 5.1 原子行为

Playwright 提供统一包装器，使测试在运行时和静态检查时都能关联稳定行为编号：

```ts
behaviorTest(
  'FIN-VERIFY-CANCEL',
  '财务可以撤销核销并恢复未核销余额',
  async ({ page, scenario }) => {
    // 只执行并验证撤销核销这一目标行为
  },
)
```

### 5.2 完整旅程

完整旅程可以引用多个原子行为，但不替代这些行为的独立失败定位：

```ts
journeyTest(
  [
    'DEP-CREATE-DRAFT',
    'SRC-CREATE-ORDER',
    'FIN-GENERATE-RECEIVABLE',
    'FIN-VERIFY-CREATE',
  ],
  '从建团到核销的最薄财务闭环',
  async ({ page, scenario }) => {
    // 串联验证
  },
)
```

### 5.3 目录校验

快速校验任务必须检查：

- 行为编号重复或格式错误；
- 能力、风险和主验证层非法；
- 测试引用不存在或已废弃行为；
- 关键行为没有主验证层测试；
- 目录声明已覆盖但测试无法发现；
- 新代码区域无法映射到任何业务能力。

## 6. 未知行为发现

### 6.1 静态候选

静态工具扫描并形成结构快照：

- 应用路由；
- 菜单和页面入口；
- 权限能力和角色可见性；
- 表单提交、主要操作按钮、表格操作列；
- 状态条件分支；
- 抽屉、弹窗和二级工作区入口。

### 6.2 运行时候选

不同角色登录后访问已知页面，记录实际可达路由、可见交互控件、可访问名称、隐藏或禁用入口、控制台错误和请求错误。发现过程默认只读，不自动执行写操作。

### 6.3 候选确认

静态或运行时快照出现差异后，AI 可以追踪事件处理器、权限和业务状态并生成候选 YAML；人工最终将候选判断为新行为、现有行为的新入口、普通 UI 操作或无需登记的展示控件。

禁止使用盲目点击所有控件的爬虫证明业务覆盖。代码覆盖率只能辅助发现未执行代码，不能替代业务行为目录。

参见 [ADR-0042](../../adr/0042-machine-discovered-human-confirmed-test-impact.md)。

## 7. 测试数据与场景工厂

### 7.1 数据隔离

- CI 每次运行使用迁移和固定种子构建的临时数据库，结束后整体销毁；
- 本地默认使用独立 E2E 数据库，禁止自动重置开发者日常数据库；
- 每轮运行和可变业务数据使用唯一命名空间；
- 生产数据库永远不能成为自动化回归目标；
- 启动时应验证数据库名称或显式测试标记，错误环境必须快速拒绝运行。

参见 [ADR-0040](../../adr/0040-isolated-scenario-data-for-browser-automation.md)。

### 7.2 场景工厂

Playwright 不通过 UI 重走与目标无关的全部前置步骤。场景工厂优先调用正式 API 或领域命令建立前置状态；只有正常接口无法产生的故障或历史边界，才能通过受限测试能力直接操作数据库。

```ts
const scenario = await fixtures.createVerifiedReceivable({
  agreedAmount: 1000,
  receivedAmount: 600,
  verifiedAmount: 600,
})

await page.goto(scenario.verificationUrl)
```

测试专用能力不得进入生产路由。所有测试数据应返回可复现的业务编号，失败报告不得只保留随机数据库 ID。

参见 [ADR-0040](../../adr/0040-isolated-scenario-data-for-browser-automation.md)。

### 7.3 角色会话

场景层负责准备企业管理员、财务、计调等角色的独立认证状态。每个测试获得独立 BrowserContext；可以复用只读登录状态文件，但不能共享测试中产生的可变页面或业务状态。

## 8. Playwright 编写规范

### 8.1 选择器契约

选择器优先级：

1. `getByRole`、`getByLabel` 等用户可感知语义；
2. 稳定业务名称或业务编号；
3. 无法通过合理语义区分的重要锚点，使用最少量稳定 `data-testid`。

关键入口缺少可访问名称时，优先修复界面语义。禁止依赖 Ant Design hash class、CSS 层级、`nth()` 序号、动态数据库 ID 或固定 `waitForTimeout`。

### 8.2 关键写行为的证据

成功 Toast 不构成充分证据。关键写行为必须验证：

1. 浏览器确实完成目标操作；
2. 页面出现正确业务结果；
3. 刷新后持久化结果仍正确；
4. 权限行为按需补充退出和换角色证据；
5. 财务、结算、核销或历史行为由 API E2E 或完整性检查证明业务不变量。

失败时保留 trace、截图、控制台、关键网络请求和场景业务编号。

参见 [ADR-0041](../../adr/0041-staged-browser-automation-ci-gate.md)。

### 8.3 flaky 策略

允许重试以收集诊断证据，但首次失败、重试通过的结果必须标记为 `flaky`，不能算作关键门禁的干净通过。

```text
passed   首次执行通过
failed   重试后仍失败
flaky    首次失败、重试通过
blocked  环境未能建立
skipped  经批准并有到期时间的临时隔离
```

关键行为不得通过 `skip`、固定等待或增加重试次数绕开。高风险行为临时隔离时必须记录原因、负责人和到期时间。

参见 [ADR-0041](../../adr/0041-staged-browser-automation-ci-gate.md)。

## 9. 变更影响与开发流程

### 9.1 影响分析

`behavior:impact` 根据 Git diff 执行：

```text
变更文件
  → capabilities.yaml 中的代码区域
  → 受影响业务能力
  → 对应行为编号
  → 需要运行的测试集合
```

权限、认证、路由、请求客户端、共享包或其他无法可靠判断边界的变更，回退到完整核心 smoke。影响分析以可解释和不漏跑为优先。

### 9.2 人工声明边界

开发者不需要为每次重构手工填写完整目录，只需确认业务语义是否变化：

```text
Behavior-Impact: unchanged
Reason: 仅重构候选过滤实现，业务规则未变化
```

或者：

```text
Behavior-Impact: modified
Behaviors: FIN-VERIFY-CREATE
```

新增或修改行为时更新 YAML 和相应测试；线上缺陷修复必须补充一个修复前能够失败的回归行为。AI 可以生成草稿，代码作者负责最终业务判断。

### 9.3 自动化命令建议

```text
pnpm behavior:validate   校验目录、能力和测试引用
pnpm behavior:discover   生成静态与运行时候选差异
pnpm behavior:impact     按当前 diff 输出受影响行为和测试
pnpm behavior:report     生成风险分层覆盖报告
```

## 10. CI 与执行分层

### 10.1 PR 观察期

新增 `web-e2e-smoke` 非阻断任务，使用临时数据库、API、Web 和 Chromium 执行关键行为，收集耗时、环境失败和 flaky 数据。快速且确定性的 `behavior:validate` 可以先于浏览器任务成为必过检查。

### 10.2 核心门禁

至少连续 20 次 CI 运行没有环境型误报，且执行时间稳定在约 5 分钟内后，才把关键 smoke 升级为 required check。关键行为出现 flaky 仍视为门禁失败。

### 10.3 夜间全量

夜间执行：

- 全部关键和高风险行为；
- 完整业务旅程；
- 多角色正向与拒绝路径；
- 后续引入的视觉回归；
- 目录失配和未知候选报告。

### 10.4 高风险 PR 与发版

财务、权限、结算等高风险能力变更，在 PR 中追加对应 journey。发版必须引用近期有效的夜间全量结果；不能用一次局部绿色代替全量风险状态。

参见 [ADR-0041](../../adr/0041-staged-browser-automation-ci-gate.md)。

## 11. 质量报告

框架不输出单一总覆盖率，而分别报告：

- 已登记：是否进入业务行为目录；
- 已自动化：是否存在满足主验证层要求的测试；
- 当前通过：最近一次有效运行是否首次通过；
- 已失配：目录、代码或测试引用是否漂移。

示例：

```text
关键行为：18 / 18 已自动化，18 / 18 首次通过
高风险行为：27 / 34 已自动化，缺口 7
未映射代码区域：2
未确认候选行为：5
失效测试引用：0
flaky：0
```

关键行为要求 100% 已登记、100% 已按主验证层自动化且最近有效执行通过。高风险缺口明确展示并持续收敛；普通和展示行为不使用浏览器覆盖率制造虚假目标。

参见 [ADR-0039](../../adr/0039-automation-coverage-by-risk.md)。

## 12. 第一条纵向试点

第一阶段选择“财务核销＋撤销核销＋计调权限拒绝”，而不是继续扩展简单页面冒烟。

### 12.1 场景

场景工厂创建同一组织内的发团、¥1,000 应收和 ¥600 未核销收款。

### 12.2 原子行为

1. 财务角色核销 ¥600：页面应收未结金额变为 ¥400，刷新后保持，核销历史存在；
2. 财务角色撤销核销：未核销余额恢复，刷新后保持，历史记录不被删除；
3. 计调角色无法进入全局财务核销入口，也无法调用对应受限能力；
4. API 辅助证据证明金额守恒、往来方匹配和组织隔离。

### 12.3 试点价值

该切片同时验证行为目录、风险分级、场景工厂、角色会话、真实交互、刷新后证据、API 不变量、失败产物、影响分析和 CI 分层，足以判断框架架构是否成立。

## 13. 分阶段实施

### 阶段一：框架骨架与核销试点

- YAML Schema、目录校验和风险报告；
- `behaviorTest()`、`journeyTest()`；
- `behavior:impact`；
- 独立数据库、场景工厂和多角色 fixture；
- 核销纵向试点；
- 非阻断 CI 和失败产物。

### 阶段二：全项目候选盘点

依次盘点认证与权限、发团、客源、执行资源、财务、供应商／伙伴、产品中心和系统管理。静态与运行时工具生成候选，人工逐项确认。

### 阶段三：风险驱动扩展

先补齐全部关键行为，再收敛高风险缺口。现有 `apps/web-e2e` 用例按行为编号逐步接入，不进行一次性重写。

### 阶段四：门禁与视觉能力

关键 smoke 达到稳定标准后升级为 required check；视觉回归作为独立能力，只覆盖固定数据、固定视口、关闭非必要动画后的少量稳定页面。

## 14. 第一阶段非目标

- 不追求每个按钮都由 Playwright 点击；
- 不使用代码行覆盖率代替业务行为覆盖；
- 不一次性重写现有 Web、API 或浏览器测试；
- 不立即把浏览器任务设为 required check；
- 不建设盲目执行写操作的自动爬虫；
- 不自动重置开发者日常数据库；
- 不把视觉回归纳入首批业务门禁；
- 不为测试暴露生产可调用的后门接口。

## 15. 第一阶段验收标准

1. 行为目录能校验重复编号、非法能力、非法风险和失效测试引用；
2. `behavior:impact` 能根据核销相关 diff 选择正确行为，公共认证或路由变更能回退完整 smoke；
3. 本地运行不会修改开发者日常数据库，CI 每次从可重建临时数据库开始；
4. 核销、撤销核销和计调拒绝三个原子行为均有稳定编号和自动化证据；
5. 关键写行为刷新后仍能证明持久化结果，API 辅助不变量成立；
6. 至少进行一次可控错误或断言变异，证明框架会真实变红；
7. 首次失败、重试通过被报告为 flaky，而不是干净通过；
8. 失败产物包含 trace、截图、关键请求和场景业务编号；
9. CI 先以非阻断方式运行并生成风险分层报告；
10. 现有 Playwright 用例保持可运行，并可以逐步关联行为编号。

## 16. 与现行验证规则的关系

当前 `docs/agents/verification.md` 仍以 API E2E 作为 CI 业务正确性主防线，并将浏览器 E2E 定义为本地可选验证。本设计在实施前不改变该事实；只有完成阶段一、经过观察期并达到稳定标准后，才修改现行验证文档和 GitHub Actions，将关键浏览器 smoke 升级为正式门禁。
