# PRD：业务对象内的 Agent 协作底座——客源单与执行资源首期

> 修订版 v2.1 · 2026-09-07。本文是本轮 **Agent 交互与用户行为 PRD**，不是字段级开发规格或技术实现方案。客源单与执行资源的交互方向已确认；配套业务规格、技术实施约定及旧任务对齐已完成，可沿用现有任务按依赖开发；实现与验收尚未完成。

## Problem Statement

计调在发团过程中，需要从沟通记录、报名名单、报价及资源确认材料中整理业务信息，核实歧义，录入客源单和执行资源，再根据实际需要提交账款。传统表单要求员工自行拆解材料；通用聊天界面又难以清晰表达业务归属、多个事项、审核依据与正式写入结果。

当前原型已经验证了业务对象优先、侧栏沟通与三栏审核相结合的交互方向。客源单和执行资源是本期落地范围，也是后续业务复用 Agent 交互底座的首批验证场景。原型认可不等于生产功能已完成，不把固定样例识别、内存状态、每类一份提案等演示限制带入正式产品。

## Solution

员工从现有业务页面唤起助手。助手以明确的业务范围、员工输入、上传材料及已有业务记录为依据，理解意图、解析与匹配对象、澄清缺失信息，形成可以核对的协作事项。查询可以直接回答，不强制建立写入任务或审核包。

侧边栏和展开的业务对象协作工作区，是同一会话的两种视图。工作区保持三栏：左侧当前业务对象、分类与相关协作记录；中间唯一会话壳；右侧本次协作事项、具体审核与确认结果。没有审核包也可以展开协作。

同次协作可产生多项客源、资源和关联账款事项。分类用于查找，不分割会话，不决定权限。确认入口只在结构化审核面；助手不得将材料解析或候选生成描述成正式业务已完成。

首期交付完整的客源单新增及其名单录入、执行资源新增与待审核资源修订、独立确认、结果回看和创建成功后的初始账款承接。普通业务页面及人工录入继续可用。

## User Stories

### 业务范围与会话

1. 作为计调，我希望从当前发团打开助手，以便系统准确识别本次协作的业务对象。
2. 作为员工，我希望看到并能调整附带的页面上下文，以便确认助手使用了正确的业务范围。
3. 作为员工，我希望缺少明确目标时先被询问，以便材料不会被写入错误的团。
4. 作为计调，我希望侧栏与展开工作区保留同一会话和未发送输入，以便切换视图不中断沟通。
5. 作为员工，我希望无需先产生审核包就能展开工作区，以便集中处理资料和澄清问题。
6. 作为计调，我希望在同一发团下找回之前的协作，以便接续未完成事项和查看依据。
7. 作为员工，我希望新建协作不删除旧会话及其产物，以便不同业务目的分别处理。
8. 作为员工，我希望普通导航到无关对象不会偷偷沿用原对象，以便避免上下文串用。
9. 作为员工，我希望通过明确的关联业务入口延续会话并看到关联范围，以便处理有关联的业务。
10. 作为计调，我希望事项列表、审核、编辑及结果页的左栏布局保持一致，以便始终知道正在处理哪个团。

### 材料与协作事项

11. 作为计调，我希望粘贴业务文本或上传受支持的资料，以便助手从真实内容中提取待录入信息。
12. 作为员工，我希望文件解析中、失败和完成状态如实显示，以便知道何时需要补充文字或重试。
13. 作为计调，我希望未知信息与明确为零、无优惠等信息区别展示，以便默认值不会冒充业务事实。
14. 作为计调，我希望每项候选能追溯到材料或已存在记录，以便判断提取是否正确。
15. 作为计调，我希望一次提供的名单与资源材料形成同次协作的多个事项，以便不用自己拆成多个会话。
16. 作为员工，我希望事项分别显示待补充、待审核、已确认或失败等进展，以便知道下一步需要做什么。
17. 作为计调，我希望切换业务分类后仍能看到其他类别事项的提示，以便不会遗漏跨类别工作。
18. 作为计调，我希望从具体审核返回事项列表后保留已处理结果，以便继续处理剩余事项。
19. 作为员工，我希望纯查询不凭空生成提案，以便区分信息了解与业务变更。

### 客源单

20. 作为计调，我希望核对客户、成人人数、儿童人数及各自单价，以便形成正确的原始团款。
21. 作为计调，我希望逐项核对团款调整的项目、增减方向、金额和说明，以便保留报价构成。
22. 作为计调，我希望分别核对无优惠或整单优惠、优惠金额及备注，以便不把优惠和业务增减混为一谈。
23. 作为计调，我希望看到原始团款、调整净额、优惠和结算金额的计算过程，以便理解最终金额。
24. 作为计调，我希望在客户与报价、调整、优惠、收款约定组内直接修订，以便无需退出会话进入另一张大表单。
25. 作为计调，我希望取消组内编辑可以放弃该次修改，以便不误改审核稿。
26. 作为计调，我希望保存组内修订后重新计算和校验，以便确认前看到最新影响。
27. 作为计调，我希望不同收款方式显示准确的定金和尾款归属，以便明确谁收取哪些款项。
28. 作为计调，我希望看到预计客户补款或返利并明确其是约定推算，以便不误认为已经到账。
29. 作为计调，我希望查看和修订材料提供的客人名单及现有业务支持的字段，以便纠正识别错误。
30. 作为计调，我希望名单数量与计费人数的差异被提示而非自动互相覆盖，以便遵循现有客源单语义。
31. 作为计调，我希望必要信息缺失或金额不合法时明确指出问题，以便完成修正后再确认。
32. 作为计调，我希望一次确认原子录入一张客源单和本次选定的名单，以便不会留下半张单或部分游客。
33. 作为计调，我希望创建成功后保留相同分组的只读结果，以便核查保存内容。
34. 作为计调，我希望在客源单创建成功后才选择是否继续提交应收，以便先完成当前业务，再决定后续财务操作。

### 执行资源

35. 作为计调，我希望资源候选明确归属具体行程日期、行程段或发团级范围，以便避免资源挂错位置。
36. 作为计调，我希望核对资源种类、项目、供应商、约定总价和备注，以便正确记录资源费用。
37. 作为计调，我希望无匹配、多匹配、停用或不符合类别的供应商得到明确提示，以便补充或重新选择。
38. 作为计调，我希望容量冲突明确显示比较依据和差额，以便决定补充确认材料或修正安排。
39. 作为计调，我希望按日期阅读、按可独立提交的资源组选择确认，以便一个有问题的组不阻止其他组。
40. 作为计调，我希望补充材料只修订受影响的待审核组，以便保留已经确认的安排和版本。
41. 作为计调，我希望多组选中后逐组显示成功或失败，以便不会误以为整批全部完成。
42. 作为计调，我希望资源写入后明确应付尚未提交，以便不将资源成本与正式应付混淆。
43. 作为计调，我希望确认资源后能够明确选择继续提交初始应付，以便在同次协作中接续账款审核。

### 可靠性与权限

44. 作为员工，我希望刷新或重新打开页面能恢复服务端认可的会话、事项和审核进展，以便不重复操作。
45. 作为员工，我希望重复点击确认或网络重试不会重复创建记录，以便避免重复客源、资源和账款。
46. 作为员工，我希望其他人修改业务或新材料更新审核包后，旧版本确认被阻止并提示刷新，以便不覆盖更新。
47. 作为员工，我希望失败时保留待审核内容和原因，以便修正后重试。
48. 作为员工，我希望明确放弃提案后不会被自动重新提交，以便控制协作走向。
49. 作为员工，我希望助手沿用我的业务权限及 Organization 隔离，以便不会绕过正常权限。
50. 作为管理人员，我希望能追溯来源、人工修订、确认人和结果，以便定位业务差异。
51. 作为员工，我希望从需要人工处理的事项回到原对象、会话和产物，以便快速继续操作。
52. 作为员工，我希望创建后的应收、应付审核显示正式业务来源、收款或付款对象及金额，以便明确确认的是账款而非实际资金。

## Implementation Decisions

### 范围与术语

- 业务对象是上下文锚点，不将会话永久独占绑定到单个对象。一个会话可关联多个业务对象与事项；具体存储关系由技术设计落实。
- 协作事项用于呈现本次要处理的业务及其进展，不建设另一个可领取、分派、手动完成的任务系统。它与现有任务、审核包和执行结果如何对应，由技术设计明确。
- 发团工作区分类为发团信息、客源管理、执行安排、财务，并有“本团全部协作”查看范围。普通业务页面的现有分区不因此重构。
- 首期主动写入能力限定在本 PRD 明确的客源、资源和创建后初始账款路径。分类名称不意味着所有该类业务都已接入 Agent。
- 独立全局聊天不作为本轮产品入口。对象/列表范围入口保留平台扩展能力，但不在首期增加跨团财务处理。

### 会话壳与布局

- 复用唯一生产会话壳与服务端会话事实；侧栏和三栏不复制消息、发送或运行状态。
- 左侧摘要字段、顺序、分类和协作记录布局不随审核阶段变化。提案版本、来源、执行状态放在右侧。用户明确切换分类或业务事实变化时才更新对应内容。
- 中间会话负责输入、解释和澄清。右侧负责事项组织、结构化修订、确认、拒绝及结果回看，不在聊天内另设业务写入确认。
- 右侧内容独立滚动，结算摘要及确认操作保持可见；编辑、确认成功及回看均不得挤掉左栏或清空会话。
- 默认展示异常与摘要；按需展开完整内容。提供键盘可操作控件、明确字段标签和禁用原因。

### 输入、候选与持久化

- 输入支持粘贴文本，以及现有资料解析链支持的文件/图片；上传界面明确实际支持格式，解析失败保留资料与重试入口，不宣称识别成功。
- 页面上下文提供范围，材料提供事实。上传内容不得改变权限或绕过确认。对象匹配使用受控查询，模糊匹配必须澄清。
- 候选保留已提供、缺失、不确定、人工修订及对应来源语义。所有默认值均不可替代未提供的业务约定。
- 会话、事项、候选修订与确认结果需可靠恢复，具有稳定身份、业务关联与可追溯版本。不能以数组位置或业务类型作为唯一身份；已有模型是否足够承载由技术设计验证。
- 同类业务可以存在多个事项；单一模板槽位不能覆盖此前结果。不得要求用户为了适配旧任务阶段而拆开同次协作。内部采用多任务、多审核包或其他映射不在本 PRD 指定，但必须满足上述外部行为。
- 字段追问和后续修订必须携带可验证的任务、审核包、字段及对象引用；人工编辑期间不覆盖相应候选，不在编辑结束后偷偷回放旧修改。
- Agent 运行、消息与审核状态必须可一致恢复；不得依赖浏览器在线或框架回调作为完成依据。优先评估已有持久工作流对这一目标的支持。

### 客源单规则

- 客户与报价、团款调整、团款优惠、收款约定、备注、客人名单完整保留现有业务语义。优惠方式为现有“无优惠/整单优惠”，不新增百分比等未经确认的规则。
- 结算金额 = 原始团款 + 调整净额 − 整单优惠；金额以现有精确金额规则计算，正式领域服务为权威，UI 预览不能另建一套不同公式。
- 客户结算、全部我方代收、分拆收款分别展示对应字段。分拆收款显示客户已收定金、我方代收尾款；全部代收显示我方代收定金与尾款。预计补款/返利需在客源规格中列明计算公式和适用条件，并核对现有业务；不能用原型对超额代收的简化限制取代真实规则。
- 名单是客源单业务支持的客人信息，不将原型的硬编码年龄、电话判断或恰好十人升级为通用必填规则。缺失/差异按实际业务校验处理，名单不自动回写计费人数。
- 组内保存仅更新可恢复审核稿，取消组内编辑保留此前候选；正式写入前重新校验全部关联字段。一张客源单及本次名单作为一个原子确认单元。
- 创建成功前不询问是否提交应收。创建成功后显示选择，员工明确继续时才准备独立账款审核。该选择本身不直接生成正式应收。
- 既有已确认客源单再次匹配时不自动重复新增，也不偷偷修改已提交账款的来源；提示明确对象及修改意图。已存在财务履历的复杂变更使用既有业务流程，本期不扩展 Agent 自动变更。

### 资源与财务边界

- 同时覆盖行程段资源和发团级资源；类别、供应商、约定总价、备注和状态规则需在资源规格中逐项明确，不新增数量、单价、容量字段，Organization 隔离必须满足。
- 日期是阅读分组，不是事务边界。什么构成可独立确认的资源组、哪些组成项不能拆开，需要在资源规格中按类别明确。组内失败回滚，跨组允许部分成功并逐组反馈。
- 材料明确存在容量等执行信息冲突时提醒，不以此硬阻断费用录入；录入结果不代表执行安排已核实。数量明细仅按需写备注。
- 新材料只更新明确受影响的未确认组，产生新版本；已确认组保留原结果。已写入业务需要变更时另起明确修改意图，不隐式覆写。
- 资源确认只写资源，客源确认只写客源及名单。初始应收/应付通过明确的后续选择和独立审核承接，重新读取正式来源及现有账款以避免重复。
- 资源名称允许基于材料整理但不得虚构；整体多服务报价按实际含义归类，不自动拆价或一律归为拼出。资源类别变化须重新校验供应商。已关闭发团不可编辑，已结清发团不可新增应付，不能把资源保存成功视为应付提交许可。
- 资源总金额必须大于0，未知金额保留待补充，免费服务记录于备注或材料。资源创建成功后才选择继续应付，默认仅列本次成功且未提交应付的资源；应付失败不回滚或重复创建资源。
- 财务分组不合并增收、应收应付、流水和核销语义。首期不提供实际收付款、核销或返利支付的自动执行。

### 服务端权威与接口约束

- 服务端校验真实目标、权限、Organization、业务前置条件并保留审计。模型和前端均不决定授权。Action Gateway 和现有领域服务是优先核对的复用机制，不把其旧业务目录或阶段限制带入新交互。
- 用户确认/拒绝使用权威 User 接口，携带审核版本及选定确认单元；重复请求返回可解释结果，版本过期不产生新业务效果。
- 候选生成不计入正式经营数据。业务写入成功、失败及确认结果必须能通过真实记录验证；只有实际效果成立才显示已完成。
- 技术设计应列出新行为与现有模型的映射及缺口，比较复用和必要调整；不能仅以旧模型无法承载为理由删减新交互。具体存储迁移和接口形态由技术设计确定，不预设第二套执行系统。

## Testing Decisions

User 已确认验收边界：以真实业务闭环为主，以领域金额/权限/版本校验作为必要补充。测试外部行为和业务效果，不测试组件内部状态或提示词文字。确认日期：2026-09-07。

- 主验收入口：员工从业务页提供材料、打开事项、修订并确认，随后通过正式业务读取验证记录、关联和金额。复用现有浏览器场景与真实 API/数据库隔离测试数据，不只证明原型按钮能点击。
- 模型/解析可在确定性回归中替换为受控材料结果，但必须经过真实候选、审核和业务写入链；另以有限真实资料检验提取、来源与澄清，不把模拟识别测试当作 OCR 正确性证明。
- 既有测试基础：客源表单金额与收款推算、来源金额变更、资源金额/供应商过滤、持久审核包、多设备恢复、工作流恢复与资料解析失败测试。优先扩展这些入口，不另建并行测试体系。
- 只在有必要时使用小范围精确金额测试；权限、事务和版本冲突通过正式服务接口验证。沿用项目分层验证门禁，不默认在本地跑全套 API E2E。

| 验收场景 | 必须观察到的结果 |
|---|---|
| 仅检查已有业务 | 返回真实查询结果，无无来源候选，无业务写入 |
| 没有审核包展开协作 | 同一会话和输入保留，右侧解释当前状态 |
| 一份名单及资源材料 | 同次协作出现两个业务事项；筛选不会丢失其他项 |
| 报价含增减及优惠 | 62,800 + 600 − 400 − 2,000 = 61,000；修订后预览与正式记录一致 |
| 无优惠/缺少优惠信息 | 明确无优惠可按零计算；缺少信息不伪装为已确认无优惠 |
| 分拆收款缺尾款 | 明确待补充；录入不凭空填零；合法补齐后恢复确认 |
| 客源及名单确认失败 | 单据与本次名单全部回滚，审核内容保留 |
| 客源创建成功 | 分组只读结果与稳定左栏；此时才可选择继续应收 |
| 材料显示容量冲突 | 展示依据与提醒，允许确认费用；结果不宣称运力满足 |
| 补充车队确认材料 | 只更新对应未确认组版本，已写入组不重复提交 |
| 重复点击/网络重试 | 同一确认不会生成重复单据、资源或账款 |
| 并发修改/旧审核版本 | 拒绝过期确认，显示差异或刷新指引，不覆盖新数据 |
| 页面关闭/刷新恢复 | 原会话、未处置审核、已确认结果及部分成功进度一致 |
| 无权/跨 Organization | 不可读取或写入目标，不因 Agent 增权 |
| 确认后准备账款 | 来源为正式记录，账款需独立审核，不登记流水或核销 |
| 拒绝提案 | 不写业务，保留处置历史，不自动重新提案 |

## Out of Scope

- 独立全局 Agent 聊天、任务中心、可分派待办、全系统 Agent 控制台。
- 所有业务模块一次性 Agent 化；发团信息修改、建团流程重做、合作伙伴及供应商档案写入不属于本期。
- 跨团回款、对账分摊、实际收付款、核销及既有财务履历的自动调整。
- 自动寻找/预订供应商、无材料生成资源方案或凭空补齐客源事实。
- 无限制格式/大小的资料解析、新训练 OCR 模型及另建模型运行框架。

### 待审事项修订交互补充

新材料与人工修改冲突时保留人工值并展示新建议及来源，由用户选择，未解决只阻止该事项确认。编辑过程中不覆盖输入，提示新结果，保存/取消后展示差异。同一事项保留一条记录，右侧可展开历次修改的前后内容、来源与修改者，旧版只读且不提供整份回滚。执行资源详见 R15–R17。

未人工修改且新材料明确替代旧值时，可更新待审候选并展示差异，不额外要求采纳；有效性不明则保留冲突。针对该事项的新材料未处理完时暂停该项确认，失败可重试、文字补充或明确本次不采用，其他事项不受影响。详见执行资源 R18/R19。

用户已处理的具体冲突，重复材料或再次识别不重新提醒或阻止确认；保留处理记录，只有新的实质信息才重新核对。文件名或识别运行变化不构成新信息，见执行资源 R20。

### 确认与恢复交互补充

确认结果未知时先自动核对，持续未知提供重新查询，不判为创建失败，也不开放该项修改或重新创建；其他独立事项可继续。结果按项展示，业务失败修改后重新确认，条件未变的已知技术失败才可直接重试，不提供混合“全部重试”。提交开始后不提供撤销，离开或关窗不取消后台写入，重新进入恢复结果；成功后的更改走正式业务入口。见执行资源 R21–R23。

多选提交中，仅某项自身失败时继续其他已选独立项目，各项仍实时校验，结果逐项展示；不扩大到未选项目。见 R24。共同条件失效时停止尚未执行项，显示“未执行”与原因，成功结果保留；恢复后用户显式继续剩余项目并重新校验，内容或版本变化先重新审核，不自动恢复提交，见 R25。
