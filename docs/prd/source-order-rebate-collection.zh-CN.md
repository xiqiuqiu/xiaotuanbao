# PRD：客源代收轧差、定金/尾款分账与返利应付

**状态**：已定稿（产品六问 2026-07-27；grilling 边界补钉 2026-07-27；落账时机修订 2026-07-28；Issue [#187](https://github.com/xiqiuqiu/xiaotuanbao/issues/187)）  
**Menu Key**：`/departure`（客源单 / 发团概览）；应付侧复用 `/finance/*` 与 Partner 往来账款；确认单在合作团单·客源  
**域词汇**：见根目录 [CONTEXT.md](../../CONTEXT.md)（重点：Collection Split、Partner Collected Deposit、Customer Settlement Receivable、Guest Collection Receivable、Source Order Rebate Payable、Source Order Actual Collection Settlement、Settlement Amount、Departure Financial Summary）  
**决议来源**：[ADR-0033](../adr/0033-source-order-rebate-and-split-collection.md)；六问定稿；grilling 补钉；2026-07-28 补款落账时机修订；部分取代 ADR-0002「付给合作方仅手工」；修订 ADR-0010「路径之和=结算金额」

---

## Problem Statement

地接在客源业务中经常按合作方「收客价」向游客代收定金与尾款，地接最终只应得团款（结算金额 S）。现系统强制「客户已收 P + 我方代收 G = S」，且客户补款应收金额等于 P；游客代收仅一张应收；多收部分无法结构化为付给合作方的返利，只能堆在流水或靠手工应付。结果是：定金很大/很小时轧差语义错误、代收大于团款时无法表达返利、定金与尾款账单无法分开、发团概览看不到返利，且 G>S 时团款收款进度会被代收溢价扭曲。

## Solution

按 ADR-0033 改造客源收款模型：

- 地接与合作方现金往来只看地接代收 **G** 与结算金额 **S**：客户补款 = `max(0, S−G)`，返利应付 = `max(0, G−S)`；合作方已收定金 **P** 不进公式。
- 录单分别录入定金与尾款；**G约定**做计划预估与生成补款，**G实收**（已核销到定金/尾款节点的合计）做齐账后校正与返利落账。
- 代收场景「生成应收」建适用的定金/尾款 Guest 节点，并在 **S−G约定>0** 时**同批**按 G约定创建客户补款应收；**返利**仍在 Guest **齐账核销后**按 G实收自动落账（不提供提前按实收结算；齐账后无需再点按钮）。
- 发团概览拆开**团款收款进度**与**游客代收进度**，返利单独统计；往来确认单将「客户已收押金」映射为 P，客户补款单独列。

## Testing Seam（已确认）

**单一主 seam：客源单金额与路径编排（Source Order amount / path orchestration）。**

覆盖：录入派生与校验、生成应收（游客期次 + 约定补款）、齐账后按实收校正补款/落返利、约定变更同步、发团概览团款/代收/返利口径、确认单 P/补款列映射。不新开平行佣金引擎；齐账落账与概览统计均为该 seam 下的行为，不另拆 seam。

## User Stories

1. As a 计调, I want 在客源单上分别录入定金与尾款, so that 约定代收结构与客户口头账单一致。
2. As a 计调, I want 选择「全部客户结算 / 全部我方代收 / 合作方收定金+我方收尾款」, so that 系统按场景生成正确路径。
3. As a 计调, I want 抽屉预览显示 S、P、G约定、预估客户补款与预计返利, so that 保存前能看懂轧差。
4. As a 计调, I want 文案标明「客户已收（定金）不计入客户补款金额」, so that 不会把 P 当成客户补款应收。
5. As a 计调, I want 当 G约定≥S 时提示生成应收不创建客户补款, so that 代收已覆盖团款时预期清晰。
6. As a 计调, I want 当 G约定>S 时看到预计返利, so that 知道多收部分将付给合作方（齐账后再落应付）。
7. As a 计调, I want 允许 P 大于 S, so that 能如实记录合作方大额定金。
8. As a 计调, I want 保存时不再强制 P+G=S, so that 可按收客价录入地接代收。
9. As a 计调, I want 代收场景 G约定 必须大于 0 才能保存, so that 与「全部客户结算」不混淆。
10. As a 计调, I want 允许全部我方代收时某一期约定为 0（另一期 >0）, so that 可录「只收一笔」式全代收。
11. As a 计调, I want 「全部我方代收」在生成应收时创建定金代收与尾款代收两张游客应收（金额为约定；约定为 0 的期次不建节点）, so that 账单可分开跟进。
12. As a 计调, I want 「合作方收定金+我方收尾款」生成应收时只创建尾款代收且不为合作方定金开地接定金应收, so that 钱在合作方处不会误记为地接游客应收。
13. As a 计调, I want 「全部客户结算」生成应收时创建金额为 S 的客户结算路径且不生成游客代收与返利, so that 无地接代收时路径干净。
14. As a 计调, I want 代收场景当 S−G约定>0 时生成应收同批创建客户补款（金额=S−G约定）, so that 团款缺口在应收列表可见可跟进。
15. As a 计调, I want 代收场景生成应收时仍不创建返利应付, so that 半收款状态不会出现可误付的预计应付。
16. As a 财务, I want 游客代收齐账后系统自动按 G实收校正客户补款并生成或更新返利, so that 不必再点「按实收结算」。
17. As a 财务, I want G实收仅统计已核销到定金代收/尾款代收节点的金额, so that 未核销流水不会被结算吃掉。
18. As a 财务, I want 未齐账时不落返利, so that 没收齐就不办返利。
19. As a 财务, I want 齐账后 API 仍可幂等重跑按实收落账, so that 运维可补救而不开放提前入口。
20. As a 财务, I want 客户补款应收金额在生成时为 max(0, S−G约定)、齐账后校正为 max(0, S−G实收) 而非 P, so that S=5000、P=4500、G实收=1000 时补款为 4000。
21. As a 财务, I want 齐账后若 S−G实收≤0 则关闭未 touch 的客户补款节点, so that G 已覆盖 S 时无多余客户应收。
22. As a 财务, I want 返利以应付开给发客 Partner 且金额为 max(0, G实收−S), so that 付款核销走现有应付流程。
23. As a 财务, I want 定金/尾款流水核销到对应游客应收, so that 资金与账款对齐。
24. As a 财务, I want 返利付款流水核销到返利应付, so that 多收不长期只趴在未核销收入。
25. As a 财务, I want 系统不强制出团后 N 天或每周自动出返利付款, so that 可按自有节奏（如周结）办理。
26. As a 计调, I want 游客代收节点尚无有效核销且补款未 touch 时可改收款方式或定金/尾款并同步 Guest 与补款节点, so that 录错还能改且不与节点分叉。
27. As a 财务, I want 任一 Guest 节点已有有效核销后锁定约定变更, so that 符合有履历后明确调整原则。
28. As a 财务, I want 补款或返利节点已有有效核销后不能静默重算, so that 须先撤销核销或走明确调整。
29. As a 计调或财务, I want 发团概览拆开展示团款收款进度与游客代收进度, so that G>S 时两套事实不被混成一个百分比。
30. As a 计调或财务, I want 团款收款进度分母为各单 S 合计、单笔分子为 min(Guest已收,S)+客户补款已收, so that 游客已收≥S 时团款进度到 100% 且不超过 100%。
31. As a 计调或财务, I want 游客代收进度分母为 G约定、分子为 Guest 节点已收, so that 能单独看到代收账单进度。
32. As a 计调或财务, I want 发团概览展示返利预估与已确认应付/已付/未付, so that 不必钻进应付列表才知道本团返利。
33. As a 计调或财务, I want 返利与代收溢价不计入结算应收分母与团款收款进度, so that 概览进度不被扭曲。
34. As a 财务, I want 全局应付与合作伙伴往来账款能看到返利应付, so that 对账与付款入口统一。
35. As a 计调, I want 返利落账与补款齐账校正同属客源路径编排, so that 不会漏建或多建。
36. As an agent/developer, I want 使用 CONTEXT 与 ADR-0033 规范名（返利，非返佣）, so that 文案与领域一致。
37. As a 产品/财务, I want 往来确认单「客户已收押金」映射为客户已收（定金）P 且客户补款单独列, so that 对外签章口径与新账一致。
38. As a 产品/财务, I want 往来确认单返利列可后置, so that 第一版先修正 P/补款映射。
39. As a developer, I want 开发阶段允许破坏性重建数据且不做旧 P+G=S 长期双轨, so that 实现不被兼容分支拖垮。
40. As a 财务, I want 验收例 S=5000 三组在齐账按实收校正后金额正确, so that 与客户确认口径一致。

## Implementation Decisions

- **权威决策**：ADR-0033；CONTEXT 词条；部分取代 ADR-0002；修订 ADR-0010。
- **单一 seam**：客源单金额与路径编排（含按实收结算、概览双进度、确认单 P/补款映射）。
- **模块边界**：Departure/客源单负责 S、P、G约定、轧差与路径规格；Finance 拥有收付款节点、流水、核销；Departure finance facade / overviewStats 拆开团款收款进度与游客代收进度并增加返利口径；确认单导出改映射；不把返利或代收溢价并入结算应收分母（ADR-0020 / ADR-0033）。
- **公式**：

```text
客户补款 = max(0, S − G)
返利应付 = max(0, G − S)
```

  P 不进公式。全部我方代收：`G约定 = 定金 + 尾款`；分拆：`P = 定金`，`G约定 = 尾款`。  
  **G实收** = 本单定金代收与尾款代收节点上的有效已核销合计（不含未核销流水）。
- **落账时机（补款 / 返利不对称）**：代收场景「生成应收」建适用 Guest 期次，并在 **S−G约定>0** 时同批按 G约定建客户补款。**返利**仍在 Guest **齐账核销后**按 G实收生成或更新。齐账后按 G实收校正补款（未 touch；若已覆盖则关闭）。全部客户结算仍在生成应收时建金额为 S 的客户结算路径。
- **按实收结算**：门槛为相关定金/尾款节点均已结清；**不**提供提前结算。补款/返利已 finance-touch 后不得静默重算。产品 UI 去掉「按实收结算」按钮；齐账后自动触发校正/落返利。
- **硬拦**：金额 ≥0；代收场景 G约定>0。不要求两期均 >0；不因 P>S 或 G 与 S 关系拦截。
- **约定变更**：Guest 节点无有效核销且补款/返利未 touch 时，可改收款方式/定金/尾款并同步 Guest 与补款节点；已有 Guest 有效核销则锁定。
- **概览**：团款进度分母=各单 S 合计，单笔分子=`min(Guest已收,S)+客户补款已收`；游客代收进度相对 G约定；返利单独统计。
- **确认单**：对外「客户已收押金」= P；客户补款单独列；返利列后置。
- **废除**：强制 P+G=S；客户补款应收=P；以 P≤S 硬拦；生成应收时按 G约定先建**返利**；旧口径长期只读双轨。
- **Schema/API**：客源单持久化定金、尾款（或等价期次）；路径规格支持定金代收、尾款代收、客户补款（生成时）、返利应付（齐账后）；齐账校正动作；概览增加代收进度与返利聚合。
- **UI**：抽屉分区——客户结算 / 代收约定 / 预计结算差额（预估补款与返利）；列表区分定金代收、尾款代收、客户补款、返利；概览双进度 + 返利卡。
- **历史数据**：开发阶段允许破坏性重建；不做旧口径长期双轨兼容。

## Testing Decisions

- 只测外部行为：给定录入、生成应收、核销、齐账校正/落返利与概览/确认单读取，断言节点是否存在、金额、对手方类型、进度与导出列；不测内部拆分实现。
- 主模块：客源单金额与路径编排（含生成时补款、齐账校正与概览口径）。
- 先验：现有客源金额计算/校验单测、生成应收与 departure/partner 相关 e2e、概览 stats、往来确认单导出测试。
- 必过验收例（S=5000）：

| 阶段 | P | G | 期望 |
|------|---|---|------|
| 生成应收（G=G约定） | 4500 | 200 | Guest 尾款 200 + 客户补款 4800；无返利 |
| 生成应收（G=G约定） | 200 | 6000 | Guest 定金+尾款；**无**补款、**无**返利 |
| 齐账后（G=G实收） | 200 | 6000 | 返利 1000；无补款（或补款已关闭） |
| 齐账后（G=G实收） | 4500 | 1000 | 补款校正为 4000；无返利 |
| 齐账后（G=G实收） | 4500 | 200 | 补款 4800；无返利 |

- 行为回归：全部客户结算无返利；合法溢价代收不得再因旧 P+G=S 校验失败；生成应收后代收场景可有补款、仍无返利节点；齐账前未核销流水不计入 G实收；团款进度在 Guest 已收≥S 时为 100% 且不因溢价超过 100%；确认单押金列=P。

## Out of Scope

- 往来确认单强制增加**返利**列（后置确认）。P/补款列映射修正**在范围内**。
- 系统按周或按出团后天数自动生成返利付款；新核销后自动重算已 touch 的补款/返利。
- 用「定金很小」阈值判断是否开客户补款。
- 返利做成负应收或冲减结算金额。
- **生成应收时按 G约定先建返利应付**（仍禁止；半收款可误付）。
- 资源应付、拼出等成本侧改造。
- 新建独立佣金/返佣子系统。
- 经济利润展示（客户口袋 ≈ P+返利−补款）作为第一版必做指标。
- 生产级旧 `P+G=S` 长期只读兼容分支（开发阶段直接重建）。
