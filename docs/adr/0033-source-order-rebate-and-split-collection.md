# 客源代收轧差、定金/尾款分账与返利应付

客源单收入侧由「结算金额 S + 收款拆分」驱动应收。现网 `split` 强制 **客户已收 P + 我方代收 G = S**，且 **客户补款应收 = P**；游客代收为单节点；地接多收后付给合作方（返利）在 ADR-0002 中规定第一版仅手工应付。业务确认：地接最终到手目标为 **S**；与合作方之间的现金往来只看地接代收 **G** 与 **S**；合作方已向游客收的定金 **P** 不进入补款/返利公式；录单须拆开定金与尾款；向游客收的定金/尾款分两张应收（在适用场景下）；返利为对 Partner 的应付，约定预估、实收结算，办理无固定系统截止日，并须在发团概览等统计面可见。

## Decision

### 核心公式

```text
客户补款 = max(0, S − G)
返利     = max(0, G − S)
```

- **S**：客源单结算金额（地接应得团款）。
- **G**：地接向游客代收合计；分 **G约定**（录单计划）与 **G实收**（归集到本单地接代收路径的收入，结算时用）。
- **P**：合作方已向游客收取的定金，为业务事实；**不进入**上式。
- 计划期用 G约定算预估补款/返利；结算期用 G实收校正账款金额。**客户补款**与**返利**落账时机不对称（见下）。

核对例（S=5000）：P=200、G=6000 → 返利 1000、补款 0；P=4500、G=1000 → 补款 4000、返利 0；P=4500、G=200 → 补款 4800、返利 0。

### 收款场景与生成

| 场景 | 游客侧应收 | 客户补款应收 | 返利应付 |
|------|------------|--------------|----------|
| 全部客户结算 | 无 | 金额 = S（沿用客户结算路径）；**生成应收时**即建 | **无** |
| 全部我方代收 | **定金代收 + 尾款代收** 两张 Guest 应收 | 仅当 S−G约定>0：**生成应收时**按 G约定建，金额 = S−G约定；齐账后按 G实收校正 | 仅当 G实收>S：齐账后按 G实收建/更新，对手方 = 发客 Partner |
| 合作方收定金 + 我方收尾款 | **仅尾款代收**；P 不开地接定金应收 | 同上 | 同上 |

录单至少录入：**S**（可由现团款派生）、**定金**、**尾款**（按收款方式显隐）。  
全部我方代收：`G约定 = 定金 + 尾款`。分拆：`P = 定金`，`G约定 = 尾款`。

废除强制 `P + G = S`；废除「客户补款应收金额 = P」。  
「客户已收不能大于结算金额」不再作为 P≤S 的硬拦业务依据（P 可大于 S）。硬拦仅：金额 ≥0；代收场景 G约定>0（否则应改选全部客户结算）。不要求定金与尾款两期均 >0；P>S、G与 S 的轧差关系不拦截，由预览明示补款/返利。

### 落账时机（补款 / 返利不对称，2026-07-28 修订）

- **客户补款（代收场景）**：**生成应收时**即按 **G约定** 判断；若 `S−G约定>0`，一并创建客户补款应收（金额 = `S−G约定`），与适用 Guest 期次同批出现，便于跟进「团款缺口」。游客代收齐账后按 **G实收** 校正金额（未 finance-touch 可改金额；若 `S−G实收≤0` 则关闭未 touch 的补款节点）。不提供「提前按实收结算」按钮。
- **返利应付**：**仍不**在生成应收时按 G约定先建（避免半收款状态出现可误付的预计应付）。仅在相关 Guest 节点**全部结清**后按 **G实收** 自动生成或更新；齐账后 API 可幂等重跑。系统 **不** 支持未齐账提前落返利。
- 补款或返利已 finance-touch 后不得静默重算，须先撤销核销或走明确调整。

### 返利与展示

- 返利是 **应付给合作方**，不是负应收，不冲减 S。
- 发团概览：**团款收款进度**（相对 S）与 **游客代收进度**（相对 G约定）拆开；返利（预估/已确认/已付/未付）单独统计；**不**把返利或 G>S 的代收溢价并入结算应收分母或抬高团款进度。
- 办理时机由财务自定（常见尾款齐后、可周结）；系统 **不** 设固定截止日，**不** 第一版做按周自动出账。

### 与既有 ADR 的关系

- **部分取代** ADR-0002 中「付给合作方第一版仅手工应付、不从客源单结构化触发」——返利路径改为可派生应付；其它手工其他应付仍可存在。
- **修订** ADR-0010 后果「客源各路径调整后金额之和须与结算金额一致」——在代收溢价场景下，**游客代收路径合计（G）可大于 S**；客户补款与返利由轧差表达，不再要求「客户补款路径 + 游客代收路径 = S」。

## Considered Options

- **仅靠流水事后用实收减 S 显示差额、不录 G约定、不生成返利应付** — 否决。待收/对账/概览会盲；与现「约定→应收→流水→核销」spine 不一致；超额易长期趴在未核销收入。
- **客户补款应收仍等于 P** — 否决。与已确认轧差不符（P=4500、G=1000 时补款应为 4000 而非 4500）。
- **返利 = P+G−S（经济利润）作为地接付出现金** — 否决。会把客户已持有的 P 再付一遍；现金返利仅为 G−S。
- **一张游客代收下用备注区分定金/尾款** — 否决。业务要求两张账单分别记录。
- **用「定金是否很小」阈值决定是否开客户补款** — 否决。不可系统化；开补款的充要条件为 S−G>0。
- **系统强制出团后 N 天或每周自动生成返利付款** — 否决。客户按自有节奏办理；系统只产出待付事实。
- **客户补款与返利一律等齐账后按 G实收再落** — **已修订（2026-07-28）**。齐账后落返利仍保留；客户补款改为生成应收时按 G约定先建，否则团款缺口在应收列表不可见、计调无法跟进补款。

## Consequences

- 需扩展客源单录入与校验、应收路径规格（定金/尾款来源或期次）、返利应付派生与实收校正；概览 stats 增加返利口径。
- CONTEXT：更新收款拆分、客户补款、游客代收、合作方结算（返利）词条；避免用「返佣」作规范名。
- **历史数据（已定）**：当前为开发阶段，允许破坏性重建（migrate reset / 重 seed）；**不**做旧 `P+G=S` 口径长期只读双轨，也**不**实现生产级「旧单兼容分支」。全部客源单按本 ADR 新语义。
- **往来确认单（已定部分）**：第一版须修正映射——对外「客户已收押金」= 客户已收（定金）P，客户补款单独列；**返利列仍可后置**。禁止继续使用「客户已收押金＝客户补款」。
- **G实收 / 落账时机（已定，2026-07-28 再修订）**：G实收＝已核销到定金代收与尾款代收节点的合计（不含未核销流水）。**生成应收**在代收场景建适用 Guest 期次，并在 `S−G约定>0` 时按 G约定**同批**建客户补款。**返利**仍仅在 Guest **全部结清**后按 G实收自动生成或更新。齐账后按 G实收校正补款金额（未 touch）。**不**支持未齐账提前落返利。补款/返利已 finance-touch 后不得静默重算。
- **约定变更（已定）**：游客代收节点尚无有效核销、且补款/返利未 touch 时，允许改收款方式/定金/尾款并同步调整对应 Guest 与补款节点（改方式可增删期次）；任一 Guest 节点已有有效核销则锁定，走撤销或明确调整（对齐 ADR-0010）。
- **概览进度（已定）**：团款收款进度与游客代收进度拆卡；返利单独统计。团款进度分母=各单 S 合计，单笔分子贡献=`min(Guest已收,S)+客户补款已收`；不把返利或 G>S 溢价抬高团款进度。
- 已 finance-touch 的补款/返利重算：第一版宜限制未介入可重算，已核销须撤销或走明确调整（对齐 ADR-0010 精神）。
