# Agent 理解诉求后查询、处理业务或澄清

已确认方向：由 Agent 结合上下文理解 User 的诉求，诉求清晰则查询或处理业务，不清晰则向 User 澄清。不以自然语言关键词词表或问号判定执行目标；补充同义词不能解决否定、操作咨询、上下文省略与混合诉求的语义差异。

这将修订 ADR-0052 中由服务端执行路由预先确定目标的边界。意图理解与完成依据校验仍是不同问题：目标分类正确，不等于业务已经完成；完成依据匹配，也不能证明意图理解正确。

已确认的处理边界：

- 清晰的业务变更按现有审核与确认规则推进。需要审核时生成审核包，不因意图清晰就直接修改正式数据，也不重复追问 User 是否确实想执行已经明确提出的变更。
- Agent 可先利用已有上下文和必要的授权只读查询消除歧义；仍存在多种合理解释时，向 User 发起持久澄清，不猜测业务对象或变更内容。
- 同一输入包含查询、清晰变更和含糊变更时，可先回答查询、为互不依赖的清晰变更形成审核项，同时追问含糊部分；存在依赖的变更一起等待澄清。已回答查询不代表整轮诉求完成。
- 执行中发现新事实或歧义时，Agent 可修正理解，暂停受影响的变更并追问，保留已取得的信息和处理进度。未解决的变更不能降级为普通回复后宣布完成。
- 由现有同一个 Agent 读取上下文、理解诉求并推进处理，不增加一次独立的模型分类调用；服务端继续负责权限、审核规则和结果校验。
- Agent 明确列出本轮需要处理的事项，服务端逐项核对实际结果：查询对应答复，变更对应审核项或业务执行结果，歧义对应待回答的问题。有事项未解决时不得宣称全部完成，不能以一个已完成的查询掩盖其他未完成事项。
- 逐项校验可以阻止已识别变更缺少结果时假完成，但不能证明 Agent 没有漏理解诉求；意图理解质量需另以语义评测验证。

实施范围：统一普通会话、建团与发团协作的意图和完成契约，各业务保留自己的权限、工具与审核规则；本次不增加新的业务能力。

验收采用两层证据：

- 确定性测试验证已识别变更不能以普通答复交差，以及混合事项、澄清和恢复不会丢失未完成部分。
- 真实模型语义评测覆盖同义改写、否定、操作咨询、上下文省略、混合请求和歧义。关键反例重复运行，记录误判和多余追问，不以预设模型输出或离线 observations 证明真实识别质量。例如「如何修改出发日？」应允许回答操作方法，「不要修改，只告诉我日期」应查询，「团名就叫九月川西吧」应提出变更。

实现核查发现：现有审核包已有多事项身份与结果记录，持久 Interaction 可承载澄清；当前单一 Headless Outcome 尚不能完整表达逐项答复、审核与澄清共存。应优先复用现有记录，并补齐事项与结果的关联；现有离线评测可复用场景，但真实模型执行与结果采集仍需补齐。

User 已确认整体共识并授权实现。
