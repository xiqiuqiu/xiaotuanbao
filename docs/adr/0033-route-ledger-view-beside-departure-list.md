# 发团管理并列「线路视图」，以客源单按路线名与出团日组织只读总览

客户习惯用「按线/按日扫客源流水」的表格，也有「只关心某一天有哪些团」的跨线扫读；且客户侧每个发团是一份独立日报，同日多团不能揉进一张表。现有发团业务主列表以 Departure 为行、扁平分页，无法承接该心智。决定在发团管理内增加与 **发团视图** 并列的 **线路视图**（见 `CONTEXT.md` Route Ledger View）：以路线名称与出团日期为对等筛选轴（可单独或组合为交集）；至少选其一才查询，都空则空态提示、不拉全量。出团日期须起止成对；**无路线时**跨度最多 7 天，**有路线时**日期跨度不限。**呈现单位是发团**：每个发团一份完整日报表（表头含出团日、路线名与团号），明细行是该团客源单；同日多发团上下分列，不做跨团或按日/按路线的金额与拼出加总，跨多天仅保留换日轻量分隔。拼出挂在该发团日报汇总，不写入客源行（系统无客源↔拼出分配关系）。金额列为客源约定口径（只读拼入价算式、原始团款、结算金额、客户已收、我方代收、备注），列名用规范名并可 tooltip 附注习惯称；不做行级「实收业务」，不混核销已收；视图只读，编辑跳转既有发团/客源路径。筛选写入发团管理 URL（`view=route-ledger` + `routeName` / `startDateFrom` / `startDateTo`），与发团视图筛选互不强绑（切换视图不自动互带语义）。

## Considered Options

- **只改发团列表列与分组**：行仍是 Departure，无法稳定呈现客人/拼入算式/按客源收款拆分，放弃。
- **客源行内硬挂拼出（复刻 Excel 同行）**：多客源×多拼出无 1:1 事实，分摊或猜测会制造对账争议，放弃。
- **第一版按 Product / 常用路线实体选线**：发团与模板/产品复制后脱钩，补永久关联范围过大；先按 `routeName` 精确归组，接受改名即新线。
- **行级「实收业务」净利**：口径未统一且常暗含摊拼出成本；第一版用单团日报合计表达结果，宁缺毋错。
- **必须先选 routeName**（原 #183 门槛）：挡住「先看某天有哪些团」的扫读；#221 改为双轴独立筛选并保留无路线 7 天上限防全量。
- **同日多发团合并一张表（rowSpan）**：把多个独立发团揉成一笔业务、跨团合计误导客户；#221 修订为一团一份完整日报。

## Consequences

- 需独立读模型/API（按路线名和/或出团日取出客源，并附**发团级**拼出与合计），不能仅扩展现有 `GET /departures` 列表列；UI 渲染单位必须是 Departure 日报，而非日表跨团展平。
- 与 ADR-0002（发团非结算单元、收入在客源、成本在资源）及往来账确认单的习惯名豁免边界一致：线路视图是系统 UI，规范名为主。
- 不替代发团运营表（单团总账本）或合作团单/往来账确认单（按 Partner）；线路视图回答「按线/按日扫到的各团日报」。
