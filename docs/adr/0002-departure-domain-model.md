# 发团领域模型：运营容器、统一资源与显式财务生成

发团（Departure）是一次具体出团活动的**运营容器**，不是财务结算单元。地接社在固定常用线路上反复收客、配资源、做核算；计调在发团内录入客源单、按行程段规划执行、添加资源（含拼出），再**显式触发**收付款节点生成。领域词汇见根目录 `CONTEXT.md`；财务三层模型（收付款节点 / 流水 / 核销）继承生产 `finance-handover-spec`，Finance 为独立上下文。

**收入侧**：客源单（Source Order）是结算单元——每条对应一家合作旅行社输送的一批客人，含团款、优惠、收款拆分。生成应收时按路径拆分：**客户补款**（往来 Partner）与 **游客代收**（往来游客档案），金额大于零才建节点，不可合并。地接向游客收全款后仍需付合作方的情况，第一版不在客源单自动生成应付，走应付管理手动录入。

**成本侧**：行程段（Itinerary Segment）按日期与目的地切段，是成本锚点。段内资源（Segment Resource）**统一**自营与拼出——`resourceKind = 拼出` 时关联 Partner（承接方），其他种类关联 Supplier。一段内可有多条、可混合；不设段级互斥「执行方式」。保存资源不产生应付；OP 点「生成应付」才创建收付款节点，规则与客源单侧 finance-touched / 来源差异一致。

**常用路线**（Route Template）为配置快照；选路线建团时一次性复制行程段与资源草稿，之后与发团实例脱钩。不复制客源、收付款节点、流水核销。

**发团状态**：编辑中 → 待结算（OP 手动）；已结清（收付款节点全部结清或关闭后系统判定）；已关闭（OP 手动归档）。**出团进度**（未开始/进行中/已结束）由日期派生，与业务状态独立。**发团类型**（独立团/拼团）为展示标签，不约束客源单数量。

曾考虑段级互斥执行方式（自营段 vs 拼出段）、拼出独立实体、发团级统一团款、保存即生成财务单据——均因不符合段内混合的实际计调习惯、或与生产财务 spine 冲突而拒绝。
