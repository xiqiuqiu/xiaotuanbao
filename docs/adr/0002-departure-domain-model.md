# 发团领域模型：运营容器、统一资源与显式财务生成

发团（Departure）是一次具体出团活动的**运营容器**，不是财务结算单元。地接社在固定常用线路上反复收客、配资源、做核算；计调在发团内录入客源单、按行程段（含一日一段骨架）规划执行、添加段资源或发团级资源（含拼出），再**显式触发**收付款节点生成。领域词汇见根目录 `CONTEXT.md`；财务三层模型（收付款节点 / 流水 / 核销）继承生产 `finance-handover-spec`，Finance 为独立上下文。

**收入侧**：客源单（Source Order）是结算单元——每条对应一家合作旅行社输送的一批客人，含团款、优惠、收款拆分。生成应收时按路径拆分：**客户补款**（往来 Partner）与 **游客代收**（往来类型 Guest，稳定键为客源单 id），金额大于零才建节点，不可合并。游客代收可按定金/尾款拆成多张应收；客户补款与返利按地接代收 G 与结算金额 S 轧差（补款=`max(0,S−G)`，返利应付=`max(0,G−S)`），详见 **ADR-0033**（部分取代下文「付给合作方仅手工应付」的第一版限制）。其它非返利的合作方应付仍可在应付管理手工录入。

**成本侧**：行程段（Itinerary Segment）按日期与目的地切段，可为跨日段或一日一段执行骨架，是按日成本锚点之一。成本费用行有两类锚点：**段资源**（Segment Resource，挂行程段）与 **发团级资源**（Departure Resource，挂发团，用于全程用车/保险/导游等）。两类资源共用 Resource Kind、供应商校验与显式生成应付规则（含拼出统一挂 Supplier，见 ADR-0032）；一段/一团内可有多条、可混合；不设段级互斥「执行方式」。保存资源不产生应付；OP 点「生成应付」才创建收付款节点，规则与客源单侧 finance-touched / 来源差异一致。发团级执行班组（司机/导游/车牌）与成本资源分离，选人不生成应付。团内增收记录不经收付款节点（原团上收入台账见 ADR-0034，已由 **ADR-0036** 取代）。详见 **ADR-0034**、**ADR-0036**。

**常用路线**（Route Template）为配置快照；选路线建团时一次性复制行程段与资源草稿，之后与发团实例脱钩。不复制客源、收付款节点、流水核销。

**发团状态**：编辑中 → 待结算（OP 手动）；已结清（OP 手动确认；前提是账款结束门槛为真——下属收付款节点全部已结清或已关闭）；已关闭（OP 手动归档）。**出团进度**（未开始/进行中/已结束）由日期派生，与业务状态独立。**发团类型**（独立团/拼团）为展示标签，不约束客源单数量。

曾考虑段级互斥执行方式（自营段 vs 拼出段）、拼出独立实体、发团级统一团款、保存即生成财务单据——均因不符合段内混合的实际计调习惯、或与生产财务 spine 冲突而拒绝。
