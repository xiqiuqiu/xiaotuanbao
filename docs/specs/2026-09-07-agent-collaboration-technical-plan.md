# 业务对象内 Agent 协作：技术落地核对与接入方案

版本 v0.10 · 2026-09-07。关联 [PRD #483](https://github.com/xiqiuqiu/xiaotuanbao/issues/483)、[客源单规格 v0.3](2026-09-07-agent-source-order.md)、[执行资源规格 v0.13](2026-09-07-agent-execution-resources.md)。本文记录当前工作区代码核对与建议实施方案；不是已实现声明，不新增产品功能或自动接受旧任务依赖。本次未改生产代码或数据库；旧 Issue 已按用户授权对齐，处理记录见下文。

## 1. 结论及范围

复用现有 Conversation、InputBatch、Workflow Worker、AgentTask、AiAction、AiReviewPackage、AiReviewRecord 和领域服务；不重建会话、执行引擎或待办系统。已有能力包括多审核包存储、来源验证、Worker 事务提交、会话恢复、确认命令幂等。主要工作是把仍绑定建团草稿的路径接到已有发团，并补足多事项生命周期、修订版本和正式写入的可靠性。

现有代码不再是“一任务只能一个待审包”：迁移已删除该唯一索引，摘要已有 `pendingReviews`。但“一次模型结果一个包”和“一次处置结束整个批次”仍存在，不能把存储支持多包等同于新交互已支持。

建议首期按一个独立确认单元对应一份审核包组织：一张客源单含本次选中名单、一条段资源、一条发团级资源，以及后续独立账款事项。多选是多个确认单元的组合，不承诺整批事务。右侧事项列表是已有权威数据的投影，不另建一套待办状态；尚未形成审核包的待补充事项从任务/追问投影。

## 2. 当前链路与准确复用范围

| 环节 | 核实到的实现 | 接入判断 |
|---|---|---|
| 会话与输入 | `AiConversationService` 保存事件、文本草稿、材料批次；读取组装 events、activeBatch、pendingInteraction、queuedBatches、draft；所有者检查存在 | 继续作为恢复真相；会话关联任务已是多对多，不能改成按业务类别各建一套聊天 |
| 模型执行 | `AiWorkflowProcessor` 使用作业认领与 generation；终态前重查执行权及权限 | 复用 Worker；浏览器只负责提交输入、展示与恢复，不成为另一执行者 |
| 候选提交 | Worker 在同一事务内执行来源验证、网关投影审核包、会话事件、批次/attempt/job 终态 | 当前该路径已具备原子提交结构，不能继续引用旧审查中的“网关不存在/全部分事务”结论；新增多项结果须维持这一结构 |
| 提案身份 | 审核包有来源会话/批次/attempt/action、schema/capability、target、proposalHash；唯一键用于同批次提案去重 | 可扩展；内容哈希用于重放去重，不得用作业务事项唯一身份，合法的两条同价同内容资源仍需可区分 |
| 确认 | `confirmDepartureReviewPackage` 校验当前权限、所有者、包版本/草稿版本、命令哈希；同事务记录处置和幂等结果 | 复用命令模式，当前效果仅写 `DepartureCreationDraft`，不是创建客源/资源 |
| 审核修订 | `patchReviewPackage` 仅覆盖 `userCorrections`；DTO 没有预期包版本，保存不递增包版本 | 明确缺口：两设备修订可能相互覆盖，确认时也难以识别修订已改变 |
| 多项处置 | `finalizeReviewDisposition` 一包确认/拒绝就将批次设为 completed；确认后创建 continuation | 明确缺口：需按剩余事项状态处理，不得提前结束其他待审项或因自动续跑改写它们 |
| 业务写入 | 客源与调整项有事务，名单另有创建方法；段资源和发团级资源各有创建服务 | 不能串行调用“建客源→逐个建游客”冒充原子创建，也不能业务提交后再单独记审核成功 |
| 初始应付 | 单资源生成已有事务、行锁和已有账款检查；批量入口处理整个行程段 | 复用单项业务保护；须接明确选择集合，保存逐项真实结果，不能直接调用整段批量入口 |

## 3. 最小接入方案

### 3.1 业务对象、会话和任务

在现有任务描述/领域 Adapter 的注册机制中接入已有发团协作，任务目标直接指向服务端解析过的正式 Departure，不制造建团草稿，也不要求重跑建团阶段。一次明确的协作目标可以持有多个独立事项；新事项不要求新开会话。只读查询沿用无写任务路径。

当前 Adapter 的方法、返回值及审核路由仍引用建团 DTO/摘要，需改为按已登记任务类型和 payloadSchema 分派。只接客源、段资源、发团级资源和初始账款所需能力，不建设任意对象/任意工具框架。未知类型或 schema 拒绝写入，历史内容可只读展示。

增加可持久查询的业务对象关联。优先由任务的领域目标及审核包 target、正式结果引用派生；若未产生任务/审核包的已发送会话无法由这些关系找回，则补最小的会话—业务对象关联记录，写入时服务端验证可见性。关联只用于定位，不授权、不复制聊天，也不意味着会话只能关联一个对象。

页面上下文、任务和具体审核焦点需能一起提交并互相验证：业务对象引用、taskId、packageId、包版本、字段/组键。当前 pageLocator/primaryTaskId 不是可信业务授权；字段追问不能只传自然语言。普通导航切换到无关对象不能静默绑定旧对象。

### 3.2 事项与审核版本

重复冲突处理（R20，已确认）：持久保存具体冲突的已核对内容、用户选择和所选值。重放同一业务信息时复用该处理结果，不重开冲突；新实质信息才重新核对。不能仅以文件名、上传次数或识别运行身份判断新冲突，也不能将一次处理扩展为对所有后续材料的永久拒绝。

补充确认（R18/R19）：无人工修改且新材料明确替代旧值时，可更新候选并展示前后差异，不增加采纳按钮，最终审核确认仍必需。无法判明有效值则保留冲突。针对该事项的补充材料解析中暂停该项确认，解析失败可重试、文字补充或明确本次不采用；不得连带阻止无关独立事项。正式确认校验必须识别相关补充材料尚未处理，不能只靠前端禁用按钮。

本轮已确认的交互（执行资源 R15–R17）：新材料与人工值冲突时保留人工值并展示建议和来源，待用户选择后才能确认该项；编辑过程中仅提示新结果，保存/取消后再展示差异。事项始终保持一条，修改记录可查前后值、来源与修改者，旧版只读，不支持整份回滚。保存编辑、采纳建议和正式确认是不同动作。

沿用审核包封装及版本化领域 schema；补齐嵌套的客源调整/名单、资源字段和账款来源结构，不能把现有 `Record<string, string | number | null>` 当作完整业务载荷。

每个新事项须有服务端认可的稳定身份，区分“同事项修订”“同提案重放”“另一条内容恰好相同的事项”。本期采用同一审核包 ID 承接修订，递增 version 并追加不可变修订记录；不为普通修订另建 superseded 包。事项身份不得依赖内容相似度找回。

修订请求必须携带 expectedPackageVersion。服务端按包状态和版本更新、递增版本并返回最新校验结果；过期请求返回冲突且保留客户端未保存输入供比较，不自动覆盖。新材料不得覆盖人工修订或已确认事项。确认命令绑定具体包版本及最终审核内容，不能在执行时偷偷合并用户未看见的另一设备修订。

父级发团版本不应成为“任何子对象新增就使本团所有审核失效”的粗粒度锁。校验依赖至少区分：本审核版本、目标发团/段是否存在和可编辑、所选伙伴/供应商有效性，以及账款提案所依赖的正式源记录。独立资源 A 成功不得无理由废弃资源 B；实际影响 B 的日期/归属/金额变化须重新审核。

### 3.3 确认、正式写入和结果

多选继续规则（R24）：已确认单项自身业务失败时继续其他已选独立项目，各项仍实时校验，不扩大选择范围。共同条件失效时停止尚未执行项并展示“未执行”与原因，成功项保留。条件恢复后由用户显式继续剩余项目，重新校验；内容或版本变化先重新审核，不自动恢复写入（R25）。已受理而结果未知的命令先回查，不能归为未执行并新建命令。

确认与恢复交互已确认（R21–R23）：请求结果未知时显示“正在核对提交结果”，自动回查，持续未知提供重新查询，期间不开放该项修改或重新创建。结果区逐项保留成功回执，业务失败修正后重新确认，内容和条件未变的已知技术失败才可直接重试；不提供混合“全部重试”。提交开始后没有撤销提交，关闭或离开页面不能取消已受理命令；回来可恢复结果，提交成功后转普通业务入口更改。不得以网络异常当作已知失败，其他独立事项不受该项结果未知影响。

每个独立确认命令按以下顺序执行：

1. 从登录身份取得 Organization/User，加载本人可处理的事项，重新核对该操作的实时权限。
2. 查稳定 decisionCommandId 和请求哈希；同键同请求返回已保存结果，同键不同请求拒绝。网络超时后复用该键，修订后的新确认使用新键。
3. 在事务中锁定/校验审核版本及必要的业务依赖，完成领域验证。
4. 通过领域写入逻辑创建正式记录；同事务写审核处置、正式结果引用和幂等结果。事务提交后才发布通知；通知丢失可以通过查询恢复。
5. 前端进入本事项结果态，其余事项继续保留。后续账款只在成功结果上由用户选择继续，再生成独立审核事项。

客源与本次选定名单必须同事务；任一选中名单行失败则该客源单整体不写入。资源逐项事务，一项失败不回滚其他项。现有领域 create 方法没有接受审核事务的统一入口，应在原领域内部整理可复用的事务写入方法，普通表单和 Agent 调用共享校验/计算，不复制财务公式、不在 Agent 层直接写业务表。

结果必须保存正式对象类型/ID、操作及确认版本、实际提交值/安全摘要、相关账款 ID 和可解释失败状态。可优先复用 AiReviewRecord 与幂等结果存储，缺少结构化引用时做最小扩展。刷新不能只读 pendingReviews；要按本人、对象、会话查询待处理及已处置记录。历史结果与当前正式记录分开标明，后续人工修改不能改写原确认回执。

多选提交使用每项稳定命令身份并返回完整逐项结果。状态不明先查询，已成功项不重做；“已有账款”显示关联记录，不能伪报成本次新建。初始应收按 F1 逐笔展示，一张客源全部适用节点整体确认、同事务写入，不提供任意节点取消；不同客源独立。F2 要求事务内先检查已有账款，历史缺失、取消、作废或金额不一致不进入补建分支；完整且一致则展示已有结果。正常命令重放先回查原结果。

### 3.4 批次与恢复

Worker 结果须支持一次材料形成多个事项；来源验证与提案持久化覆盖每项并保留共享材料引用。模型一次运行可以串行，但人类审核不能被限制为一包处理完才允许另一包存在。

`finalizeReviewDisposition` 不再将任意单包处置等同于全部完成。待审核、待补充、冲突和失败由尚未处理的事项决定；只更新被处置的事项并重新计算相关聚合状态。用户选择的后续应收/应付建立独立事项，不能由自动 continuation 授权。自动说明结果可以继续，但不得自动写业务或覆盖待审候选。

恢复读取先校验所有者及业务访问权，再从持久记录恢复对象范围、会话、事项版本与结果。SSE/即时输出只做增量展示，丢事件后重新读取；sessionStorage 只记返回位置与视图选择。会话归档、关窗口、切分类不能删除候选或改变确认状态。

## 4. 权限映射与接入门槛

| 操作 | 当前路由证据 | 新接入要求 |
|---|---|---|
| 私有会话/审核读取 | Conversation 检查 creatorUserId；审核处置检查 task.ownerUserId，均限定组织 | 继续只允许本人读取私人材料和候选；正式业务按原权限共享；对象关联查询不能泄露他人会话 |
| 新增客源、段资源、发团级资源 | 现有业务控制器 `departure:write` | 复用该业务权限并在确认时重查；能查看发团不代表能新建资源 |
| 初始应收/应付生成 | 发团子对象生成路由使用 `/departure`；不能按界面“财务”分类猜权限 | F3已确认沿用普通操作：当前初始生成使用 `/departure`，不统一要求 `financeMutate` 或 `departure:write`；领域创建仍要求 `departure:write` |
| Agent 提出能力 | 网关校验注册能力与 grantedCapabilities，Worker 终态重查授权 | 业务权限和 Agent 能力授权分别检查；未登记拒绝；材料与模型输出不授予权限 |
| 伙伴/供应商解析 | 业务服务校验组织和有效性，资源再校验类别 | 提出和确认都校验，名称/ID 不能仅相信模型；目录搜索是否可由当前业务能力调用，需与既有受控查询保持一致 |

权限政策已由 Q14/F3 确认沿用对应普通操作。代码预设计调、财务和企业管理员均有 `/departure`，财务没有 `departure:write`；运行时仍按实际权限集合，不硬编码角色名。现有审核控制器、会话服务及委托 guard 的统一发团写权限门槛须按操作拆分，不能顺带放宽业务创建。异常处理入口按访问权限展示。未查询实际数据库角色配置，尚需角色回归验证，不能宣称已修改生产权限。

## 6. 建议实施顺序与验收

下面是依赖顺序，不是新建的开发 Issue。优先复用并改写对应旧任务，避免重复排期。

| 顺序 | 可交付范围 | 必须证明的结果 |
|---|---|---|
| A | 已有发团目标、事项身份/schema、修订 CAS、多项处置与结果读取契约 | 同一会话含两条同类事项和跨类事项，修订/确认其中一项不覆盖或结束其他项；不同设备旧修订被拒绝 |
| B | 客源原子写入与三栏/侧栏真实接入 | 材料→审核→组内修订→确认→正式客源与选中名单；事务中断不留半张单；刷新恢复结果 |
| C | 段资源与发团级资源真实接入 | 归属与供应商校验，独立资源部分成功，重试不重复；仅总价也能完成 |
| D | 初始应收/应付独立承接 | 创建成功后选择，权限及来源重查，重复点击/超时/已有节点/部分失败均能核对正式账款 |

## 9. 本期技术实施约定

本节将已确认行为转成最小接入合同，是实施方案而非当前代码事实；适用于 #447 及其业务接入任务。保留现有 Worker 和领域服务，不新建工作流框架，不改普通业务字段。

### 9.1 事项、修订及对象关联

- 新增 `departure_collaboration` 任务类型及其 descriptor/adapter，目标是已有 Departure；不创建 AiCreateTask 或 DepartureCreationDraft。AgentTask 增加可空的正式发团关联，允许同团多个协作任务，不使用 AiCreateTask.departureId 的唯一约束。旧建团类型继续保留自身路径。
- 业务侧栏首次成功发送时，保存经过服务端验证的会话—发团关联；采用一个带 organizationId、conversationId、departureId 的关联表及会话/发团唯一键。它服务于尚无任务或审核包的相关会话查找，不拥有任务状态；从既有任务目标和包结果能确定的关联可回填，无法证明的旧关联不猜测。
- 一项独立确认单元使用一个 AiReviewPackage ID。首次接收类型化多项结果时，为每项分配服务器身份；同一已接受结果中的两项即使内容完全相同也各有身份。重放读取持久化的项映射，不重分配；业务上可疑重复按规格核实。
- 扩展提案身份使其包含服务器分配的项标识，而不仅是内容哈希。现有按批次/目标/哈希的唯一键必须同步迁移，否则两项同内容会误合并。同项不同版本仍是原 ID；候选、用户修订、冲突处理均以预期包版本条件更新。
- 扩展 AiReviewRecord 的修订动作及明确的 packageVersion 字段，追加保存该次前后内容、来源、操作者和冲突选择；旧处置记录不重写。目标 objectVersion 与 packageVersion 不混用。普通修订不产生新事项卡，不做整份旧版回滚。
- 新增金额/关联对象不凭缺省值补齐；领域 schema 承载数组及嵌套数据。schema 版本决定解析及校验；未知 schema 只能显示安全只读提示，不可提交。

### 9.2 服务端接收确认与持久执行

复用 AiCreateIdempotencyRecord 记录确认身份，增加可空的类型化请求快照与操作者关联；resultJson 继续保存结果，不混作请求。复用 AiWorkflowJob 增加人工审核确认作业类型及命令记录关联。此作业执行已明确确认的业务命令，不调用模型、不产生新建议，不将人工授权伪装为 Agent capability 授权。

一次多选确认的接收事务保存：批次确认键、每项包 ID/版本/操作/最终审核内容、稳定子命令键以及待执行作业。成功受理后即使浏览器关闭，服务端仍知道完整选择集合。已有活动确认命令的事项暂不接受修订；新材料保留为待处理输入，不覆盖被冻结的确认内容。执行前发现相关新材料未处理时按 R19 拒绝写入并返回待核对，不忽略新材料。空选择、重复项、跨组织/他人事项和同键异载荷请求拒绝。网络未收到受理响应时以原键查询或重发，不另发新键。

作业绑定来源会话与原输入批次用于追溯，但不复用原批次的“模型处理完成”作为业务确认结果。确认作业新增自己的类型分派、认领和重试分支；不能因默认 agent_batch 路径而再运行模型。通知只在事务提交后发布，丢通知用读取接口恢复。

每项执行前重查当前授权、包版本、相关材料是否处理完成及业务依赖。事务中完成领域写入、AiReviewRecord 和该子命令的正式结果引用；之后下一独立项继续。结果未知不能被归类为未执行；同项已成功不再调用领域创建。

- 单项业务失败记录该项原因，继续其他独立项。
- 发团关闭/授权失效等共同前置失败停止剩余未执行项，保存原因。恢复后由用户显式继续，重新校验，版本改变须重新审核。
- 明确未提交的技术失败保留相同请求快照，通过原命令的受控重试产生新执行尝试；不能更换业务身份规避幂等。终态业务拒绝后修订，使用新的包版本和新确认键。
- 技术异常导致事务回滚时，不写成功回执。连接中断而提交结果未知时，先重新查询数据库确认，不直接写入“失败”并再次创建。

无需新增权威待办表。提交中状态从确认命令/作业读取，待审状态从审核包读取，已写入结果从处置回执及命令结果读取。

### 9.3 API 读写合同

接口路径最终遵循现有 agent 路由命名；以下载荷语义必须一致，不允许前端通过聊天文本猜状态。

| 操作 | 必须传入或校验 | 返回及行为 |
|---|---|---|
| 保存事项修订 | packageId、expectedPackageVersion、类型化字段变更 | 返回新包版本、有效候选、校验与冲突；过期返回冲突，不覆盖 |
| 提交确认选择 | decisionCommandId、items[{packageId, expectedPackageVersion}]；审核快照由服务端冻结 | 返回受理身份及每项当前状态，不把受理当成功；同键异载荷拒绝 |
| 查询确认结果 | 本人/组织下的确认身份 | 每项未执行/处理中/成功/失败、原因、是否可重试及正式引用；未知不造假 |
| 查询对象协作 | 受控 departureId、可选本人 conversationId、分类及游标 | 相关会话、独立事项、待补充与已处置结果，不能只返回 pending 包 |
| 查看修改记录 | 本人可见 packageId、游标 | 不可变版本差异、来源与操作者，历史只读 |
| 继续或重试 | 原确认身份及明确选中的剩余项 | 不含成功项；先回查并重验，不自动恢复共同前置失败后的写入 |

包版本是确认快照身份，目标依赖快照另记：客源/资源创建校验发团、段、客户/供应商状态；初始账款比对正式源金额、往来对象、收款路径及已有账款。不能因为本团另一条独立资源刚新增，就使所有候选过期。依赖发生实质变化才要求重新审核。

### 9.4 领域事务接入

| 现有路径 | 必要最小改动 |
|---|---|
| SourceOrderService.create / createGuest | 领域内部提供接受调用方 tx 的创建逻辑；复用输入规范化、计算和名单校验，客源、调整及所选名单同事务。普通接口保持行为，Agent 不循环调用多个独立 HTTP |
| SegmentResourceService.create / DepartureResourceService.create | 将关联查询、状态检查和创建收口到调用方 tx；保留供应商类别等校验。不能在 Agent 层复制 SQL 或在领域写入提交后才记审核成功 |
| DepartureFinanceGenerationService | 初始应收/应付生成接受调用方 tx；外层普通入口仍可自行开启事务。Agent 增加明确的“仅正常初始生成”策略，事务内拒绝历史补建/恢复，不改变普通入口现有补建行为 |

锁顺序不凭“先锁发团再锁所有对象”统一改写。现有初始生成是先源记录、再创建节点时锁发团；已有账款修改还涉及节点锁。新接入先固定会话运行锁→任务/包→确认身份的顺序，随后复用对应领域命令锁序，禁止反向从领域服务获取会话锁。新增/确认与普通修改、关闭、作废并发必须用隔离数据库验证；死锁中止按无提交的技术失败处理，不绕过锁或扩大为自动重建。最终领域锁调整在对应任务里同时覆盖普通调用方，不只修 Agent 单一路径。

### 9.5 授权与迁移

会话访问先检查本人/组织及业务范围可见性；执行授权再按操作：创建客源/资源用 departure:write，初始账款生成沿用 /departure。同步排查 AgentReviewController、AgentTask 路由/descriptor、AiConversationService.assertAssistAccess、委托 guard、Worker 终态授权与能力注册，避免只改按钮或单个 controller。角色名不参与授权判断；Agent 受控工具能力仍另外校验。

采用增量迁移：保留旧建团任务、包、会话及回执；新可空字段先部署，旧包保留原 schema，无法恢复的旧包版本不伪造。替换旧提案唯一索引时先核对既有数据，按旧包 ID 回填服务器项身份。关联表只回填有明确证据的对象关联。不运行 db:reset-agent-run-data，不创建两套可写审核系统。新增枚举/索引及存量只读兼容必须在隔离数据库迁移演练后交付。
